# MG Desktop One 统一桌面规划

日期：2026-09-08。状态：规划草案，尚未实施业务接入。范围：浏览器中的企业统一桌面，借鉴 macOS 的菜单栏、Dock 和多窗口交互。

用户已明确的架构约束：**内部应用全部使用统一认证提供的同一套登录访问令牌。一个用户的一次登录会话，在桌面和各内部应用中使用同一枚当前有效访问令牌；业务应用不再签发自己的登录令牌或建立可独立认证的本地会话。**

## 1. 产品定位与决策

将 `mg-desktop-one` 建成 MG Inside 的统一工作入口：登录一次，在桌面里打开应用、并排查看资料、切换工作、恢复上次布局。

推荐采用 **Vue 桌面壳 + 独立来源的 iframe 业务窗口 + 统一认证令牌 + 统一 API 入口 + 轻量接入协议**。现有应用继续独立开发、部署和处理业务权限；桌面负责工作环境，统一认证负责全部内部应用的登录凭据。第一版面向浏览器，安装式 PWA 和原生外壳留待后续需求明确后评估。

macOS 的借鉴范围是空间布局、窗口层级和操作反馈。业务内容继续使用现有 Element Plus 表格、表单与研究工作台，保持清晰、紧凑和可读。

### 2.1 当前是否支持：源码核对结论

**当前实现支持统一身份登录及中心会话联动，但尚未实现用户要求的所有内部应用共用中心访问令牌。以下缺口全部计入本规划实施范围。**

| 项目 | 当前认证实现 | 共用中心令牌 | 桌面窗口接入 | 纳入调整 |
| --- | --- | --- | --- | --- |
| 统一认证 | 自有 `mg_identity_session`；提供 OIDC、按应用身份目录、中心会话有效性查询与撤销 | 部分基础已有；未形成三应用共同接受同一访问令牌的完整链路 | 当前为独立管理壳层；源码未发现现成桌面协议 | 扩展令牌签发/内省/续期/撤销；管理 API 接受统一令牌；发布认证 SDK；管理页 embed 模式 |
| Token One | SSO 回调通过 `JwtUtil.sign` 签发本地 JWT；前端保存 `mg_token`；后端以项目 `jwt.secret` 验证，并检查中心会话 | 不支持当前目标 | 有独立 Layout/AdminLayout 与内部路由；源码未发现桌面生命周期协议 | 替换本地登录 JWT 链路；接入中心认证 SDK 和统一 API 入口；精简内嵌布局；接入窗口/流式生命周期 |
| 指标知识库 | SSO 成功后生成独立随机令牌及 `authSession`；写入 `mg_expert_session`；读取本地会话后再检查中心状态 | 不支持当前目标 | 有深链接与内部未保存内容守卫；未接入桌面关闭请求 | 替换本地业务会话认证；迁移 CSRF 绑定；接入统一 API、embed 模式、关闭保护、流式与基路径适配 |
| 统一桌面 | 当前目录此前为空 | 待建设 | 待建设 | 桌面壳、窗口管理、统一 API 入口、应用目录、中心令牌接入与跨应用验收 |

复用点：中心 `/api/directory/session` 已按 subject、sessionId 和应用 membership 检查会话状态；`/api/directory/logout` 已有应用撤销权限限制。它们可以作为新内省与撤销逻辑的基础，但当前查询的是中心会话关联，不证明业务已经接受同一枚中心访问令牌。

### 2.2 跨项目实施清单

1. **统一认证项目**：确定统一访问令牌契约；基于现有中心会话实现签发、校验、失效和应用授权；补充续期与并发策略；将中心 GUI 的受保护 API 纳入同一认证体系；维护服务身份、最小授权目录与共用认证 SDK。SDK 返回稳定主体和中心认证结果，不替业务决定具体数据权限。
2. **Token One 项目**：调整 SSO 回调、JwtAuthGuard、前端 auth store、API 请求层和退出行为，停止内部网页登录 JWT 二次签发；保留原 user ID、分组、额度及业务角色；Layout/AdminLayout 增加内嵌模式，验证门户、管理页、调试与流式能力。
3. **知识库项目**：调整 SSO 回调、AuthService/Guard、前端会话初始化、API 请求与 CSRF 处理；不再创建用于内部登录的独立 authSession；保留原身份映射、体系授权、审计与乐观锁。将现有路由离开守卫复用到桌面 request-close，覆盖保存失败和 AI 运行状态；适配生产子路径。
4. **桌面项目**：实现唯一 API 入口与中心令牌传输、应用目录、窗口状态机和桌面 SDK；接入三应用，并覆盖原站独立入口。第一版通过配置管理应用，后续再补完整应用管理界面。
5. **部署与联调**：配置桌面来源白名单、CORS、CSRF、CSP、Cookie、流式代理与回调；联合验证同令牌、续期、统一撤销、授权撤销、切换账号、历史数据权限、窗口关闭、上传下载和旧凭据退出。

本轮只完成规划、源码核对和交互概念验证；上述业务前后端与生产部署均尚未修改。

## 3. 桌面布局

### 顶部菜单栏

- 左侧：MG 标识、桌面名称、当前活动应用。
- 中部：按需显示当前应用支持的操作；第一版只放窗口操作，不为每个业务功能复制菜单。
- 右侧：应用搜索、通知入口、时间、个人账号菜单。
- 个人菜单包含账号安全、桌面偏好和退出所有应用。

建议高度 36px。快捷操作有可见按钮，不要求用户记住快捷键。页面内搜索快捷键可建议 `Ctrl/Cmd+K`，必须验证浏览器冲突与 iframe 焦点；不接管系统 `Alt+Tab` 或 `Cmd+Tab`。

### 桌面区

- 采用蓝、青、淡紫的低对比渐变壁纸；业务窗口保持实色底。
- 放置用户固定的少量应用图标、可选的最近工作入口。
- 默认不堆放经营指标或无来源的统计卡片。
- “最近工作”保存应用及安全的业务路由，具体标题和数据仍需业务权限校验。

### Dock

- 底部居中，固定应用与已打开应用合并展示，以运行标记区分。
- 点击未启动应用则打开；点击已启动应用则恢复并前置，第一版每个应用默认单实例。
- 后续多窗口应用点击后展示该应用的窗口列表。
- 应用启动器显示授权应用，可按名称查找、固定和取消固定。

### 应用窗口

- 标题栏包含关闭、最小化、最大化/还原，以及应用名称和当前业务标题。
- 支持拖动、缩放、前置、左右贴靠与工作区内最大化。
- 应用内嵌模式隐藏重复的品牌顶栏和账号菜单，保留业务侧栏、面包屑、筛选和操作区。
- 应用里的确认对话框限制在该应用窗口内；全局退出、桌面搜索等由桌面壳统一展示。

设计建议：标题栏 40px，窗口圆角 14px，内容边距沿用业务的 16–24px。桌面窗口常用起始尺寸为可用工作区的 80% × 82%；知识库研究窗口默认最大化。最小尺寸由应用声明，并始终夹取到当前可用空间。

## 5. 窗口行为契约

| 用户操作/状态 | 规定行为 |
| --- | --- |
| 启动/重复启动 | 首次挂载；重复点击恢复并前置已有窗口 |
| 切换/最小化 | 保留 iframe、路由、编辑与流式任务；可通知应用降低无关轮询 |
| 最大化/贴靠 | 使用桌面可用区，不遮挡菜单栏和 Dock；还原恢复之前边界 |
| 关闭 | 请求应用确认可关闭；有改动则由应用提供保存、放弃、取消；确认完成后才卸载 |
| 保存失败/应用未响应 | 不将超时视为允许关闭；保留窗口并给出重试或明确的强制关闭操作 |
| API/AI 流式任务运行 | 应用声明是否可关闭；最小化不中断，关闭前明确取消后果 |
| iframe 内点击 | 由接入协议上报聚焦，使其成为活动窗口；不能依赖父层事件冒泡 |
| 拖动经过 iframe | 拖动期间使用透明捕获层和指针捕获，结束/取消时清理 |
| 刷新桌面 | 恢复允许保存的布局与路由，再重新校验权限；不承诺恢复未保存内容和运行中请求 |
| 失效/断网/升级 | 窗口显示可恢复错误状态；版本不兼容要求重新加载；不得主动刷新有未保存内容的窗口 |
| 账号切换/退出 | 撤销会话，清理当前用户的布局索引、最近工作和客户端缓存，刷新应用授权 |

浏览器刷新、关页与崩溃不能完全由窗口协议拦截。应用应保留 `beforeunload` 等已有提示；真正需要恢复草稿时另行设计按用户隔离的草稿存储，首版不承诺无损恢复。

窄屏建议：工作区宽度不足 1024px 时默认单窗口最大化，通过 Dock 或窗口列表切换；低于 768px 改为单页应用式布局和底部切换入口。按容器实际宽度判断，避免在 iframe 内依赖宿主浏览器宽度。桌面恢复布局时夹取越界窗口，确保标题栏始终可达。

## 6. 工程边界与接入方式

建议桌面前端使用现有团队栈 Vue 3 + TypeScript + Vite + Pinia。Element Plus 用于设置、应用管理等表单；桌面壳、Dock、窗口管理器单独实现。具体依赖版本在开工时对齐，不在规划阶段强行统一三个老项目版本。

建议目录：

```text
mg-desktop-one/
  apps/web/src/
    desktop/          # 菜单栏、桌面、Dock、启动器
    windows/          # 状态机、拖动、缩放、焦点、贴靠
    apps/             # 应用注册、启动与 iframe 容器
    system/           # 搜索、通知、偏好、登录衔接
  apps/server/        # 统一 API 入口、认证接入、应用目录、偏好
  packages/desktop-contracts/
  packages/desktop-sdk/
  docs/
```

桌面服务处理统一 API 入口、经授权的应用目录与偏好，不签发另一套登录令牌。统一认证签发的令牌经入口转交业务服务校验；身份主数据仍在认证中心，模型额度与研究资料仍在业务服务。桌面持久化只需最小存储，跨设备偏好上线时再确定数据库方案，不复用业务表作为桌面数据库。统一认证项目负责发布共用的服务端认证 SDK，桌面 SDK 只负责窗口协作。

注册项至少包含：`appId`、名称、图标、入口来源、部署基路径、内部启动路由、接入协议版本、单/多实例策略、默认/最小尺寸和能力声明。静态展示元数据可以先配置管理，最终可见应用由服务端结合中心授权过滤；业务管理角色通过各应用提供的受限能力接口解析，不能把中心管理员直接等同于所有业务管理员。

### 三种方案的选择

| 方案 | 特点 | 结论 |
| --- | --- | --- |
| iframe + SDK | 来源、CSS 和发布隔离清晰；需处理登录、焦点与生命周期 | 推荐首版 |
| 微前端运行时/模块联合 | 页面整合深入；路由、样式、依赖和卸载生命周期改造较多 | 业务跨窗口协作需求成熟后再评估 |
| 合并前端为一个大应用 | 初期整合直观；各项目发布与权限边界耦合 | 当前三个独立项目不优先采用 |

最小 SDK 事件包括：`ready`、`focus`、`title-change`、`route-change`、`dirty-change`、`request-close`、`close-result`、`visibility-change`、`auth-required`。主题同步、通知、跨应用打开作为明确声明的可选能力。

每条消息携带协议版本、应用与窗口标识、请求标识；使用精确 `targetOrigin`，同时校验 `event.origin`、`event.source` 和消息结构。窗口标识只是关联字段，不能作为授权依据；消息中不传密码、业务令牌、中心 Cookie 或任意可执行内容。`open-app` 只能传注册应用及白名单路由，不能让子应用任意导航宿主。

## 7. 统一令牌：已经确定的认证架构

### 7.1 令牌归属与校验

统一认证是内部登录令牌的唯一签发者。桌面、Token One、知识库和统一身份管理界面全部接受中心的统一访问令牌。同一用户会话的当前令牌值在请求链路中保持一致，网关不兑换为业务令牌，业务服务不再次签发本地 JWT 或 Session Cookie。

建议首版采用中心管理的高熵不透明访问令牌，服务端仅保存其摘要及会话、过期、撤销、应用授权关联。各业务通过统一认证 SDK 调用受保护的令牌内省接口，得到用户主体、会话状态、目标应用访问授权和过期时间。SDK 使用独立服务身份调用内省接口，不能把服务凭据发给浏览器。

每次受保护请求都检查令牌有效性与目标应用授权。首版不缓存“仍有效”的内省结果，以明确实现撤销成功后的下一次校验拒绝；中心不可用时拒绝受保护操作，不降级接受过期缓存。后续有性能证据再设计可量化的短缓存与撤销传播窗口。已经执行中的操作和长连接另行定义撤销行为，不能声称撤销能回滚已经完成的操作。

应用将中心稳定用户 ID 映射到原业务用户，保留原角色、数据归属、额度、审计和权限。中心允许进入应用，应用再判断能否修改某个指标或管理某个渠道。桌面入口可见性不是权限证据。

### 7.2 浏览器如何共用同一令牌

推荐拟建统一入口 `https://desktop.meta-gravity.com`（域名建议，尚未创建），同时承载桌面和受限 API 网关，例如：

```text
浏览器登录 → 统一认证签发访问令牌 T
           → 受控回调将 T 设置为统一入口的 HttpOnly Cookie

桌面 / 应用 iframe
           → 请求统一入口 /api/apps/{appId}/...
           → 网关读取 T，以同一个 Bearer T 转发
           → 业务认证 SDK 向统一认证验证 T 与目标应用授权
           → 执行业务权限检查与操作
```

Cookie 直接承载统一认证签发的访问令牌 T，不是网关另发的登录会话票据。统一入口设置 host-only、Secure、HttpOnly Cookie，并按登录流程配置 SameSite；令牌不放进 localStorage、业务路由、桌面布局或窗口消息。

应用前端可以保留现有来源，以 iframe 嵌入桌面，但需将业务 API 指向统一入口。跨来源请求携带 credentials；统一入口按精确的内部应用来源配置 CORS，启用 CSRF 与 Origin 校验。应用内受保护的身份信息和能力也通过统一入口获取，不能读取父页面 Cookie。原站独立打开时继续使用相同 API 入口与中心登录返回流程。

代理路由必须采用注册服务白名单，移除浏览器伪造的内部身份头；业务服务自身仍校验同一枚令牌。统一入口需适配 SSE、流式 POST、上传、下载、取消请求、超时与业务基路径，避免缓冲截断 Token One 和知识库的流式功能。只有注册的内部应用可接入这套令牌体系。

这样既实现用户要求的共用令牌，也避免向整个 `meta-gravity.com` 的所有子域广播登录 Cookie。应用页面来源隔离与统一 API 入口是两个独立设计层面。

### 7.3 续期、退出与迁移

- 统一认证负责有效期与续期；续期协调放在统一入口，采用单次并发刷新和令牌版本校验，避免多个窗口分别刷新。首版续期延长同一枚中心令牌，所有应用继续携带该令牌。若使用刷新凭据，也只由中心提供并在服务端集中保管，不分发给业务应用。
- 从任何应用退出都调用中心撤销当前会话，统一入口清理 Cookie；停用账号和撤销应用授权也由中心反映到后续内省结果。
- 认证页面走顶层流程，完成后返回白名单入口并恢复业务深链接。一次性回调码是传递中心令牌的临时凭证，不形成独立的业务登录状态。
- Token One 当前 `mg_token` 本地存储和本地登录 JWT 路径需要迁移；知识库当前业务 Session Cookie 校验需要替换为共用认证 SDK。这是必要后端改造，不能只改桌面登录页。
- 中心的现有管理会话机制也需纳入统一令牌校验，保留必要的认证流程临时状态。原业务身份映射继续保留，不迁移或重建业务历史数据。
- Token One 面向模型 API 调用的 API Key 是另一种产品凭据，现有 `/v1/*` 调用契约不因网页统一登录而变更；这里统一的是内部应用用户登录访问令牌。
- 分阶段在测试环境切换认证适配器，移除旧凭据客户端缓存，验证后按应用灰度。最终内部应用入口只接受中心统一令牌；回滚以明确的应用版本和认证模式为单位，不能无限期双轨接受旧登录令牌。

### 7.4 内嵌与部署

业务页面使用 CSP `frame-ancestors` 精确允许桌面来源；桌面使用 `frame-src` 限制可加载来源。一起核对应用、反向代理和 CDN 的 CSP/X-Frame-Options。iframe sandbox、上传下载和剪贴板权限按实际能力配置验证。

本地验证统一入口与三个业务前端的来源、CORS、Cookie、CSRF 和回调路径；不要混用 localhost、IP 与生产域名。知识库生产带 `/knowledge-base-inside` 子路径，资源路由和 API 路径需要专项验证。

## 8. 分阶段实施与验收

以下为单名熟悉项目的全栈工程师估算，含基本验证，不是排期承诺；统一令牌与线上响应头验证完成后再收敛工期。

| 阶段 | 建议工作量 | 交付与通过条件 |
| --- | --- | --- |
| P0 统一令牌与接入验证 | 3–5 人日 | 中心签发、内省与撤销契约；同一令牌通过统一入口访问各服务；内嵌、子路径与生命周期样例；明确认证及桌面 SDK v1 |
| P1 桌面骨架 | 4–6 人日 | 菜单栏、桌面、Dock、启动器、窗口状态机、拖动缩放、最小化最大化、基础贴靠；模拟应用可完整操作 |
| P2 首批真实应用 | 7–11 人日 | 中心和业务认证适配、统一 API 入口、三应用 embed 模式、权限目录、关闭保护、路由恢复；独立入口接入同一令牌 |
| P3 体验收敛 | 3–5 人日 | 偏好与布局、应用/入口搜索、错误恢复、窄屏与键盘操作、性能测量；试点账号验收 |

首版合计约 17–27 人日（约 4–6 周）。全局业务全文搜索、跨应用消息聚合、跨设备工作空间、多虚拟桌面、文件管理器、原生托盘和系统级快捷键不计入首版。

建议正式第一步实施 **统一令牌纵向链路 + 知识库窗口样例**：先证明中心签发的一枚访问令牌可被桌面与业务共同校验且统一撤销，再用知识库验证宽布局、深链接、编辑保护和流式功能。P0 通过后再扩展完整桌面。

首版验收场景：

1. 普通用户登录后，桌面与三个内部应用使用中心签发的同一访问令牌；测试中只比对脱敏摘要，不记录原令牌。应用不生成独立登录凭据，未获授权的业务接口拒绝访问。
2. 三个应用同时开窗，点击内容可以前置，最小化不重载，拖动跨 iframe 不丢失操作，缩放后业务弹层位置正确。
3. 编辑知识库后关闭，依次验证取消、保存成功、保存失败、放弃、应用无响应；保存失败和协议超时都不会卸载窗口。
4. 刷新与分享安全深链接恢复到正确应用；知识库带部署前缀，且 URL、偏好和消息中均没有凭据。
5. 从任一应用或桌面退出后，撤销接口成功返回后的新请求拒绝旧令牌；续期并发时各窗口继续使用同一枚已续期令牌。停用账号、撤销应用授权、中心不可用分别验证。
6. 三应用中的文件上传、下载、剪贴板、AI 流式响应和内部弹窗按各自实际功能运行；关闭与最小化分别验证。
7. 在 1440、1024、768、390px 下窗口标题与主要操作可达；键盘可切换和操作窗口，减少动态效果设置生效。
8. 记录设备、浏览器与网络条件后测量桌面首屏和三应用并开内存；已加载窗口切换不触发重新加载，未启动应用不预挂载 iframe。

## 9. 开工前需要核实的有限事项

- 三个实际部署入口的响应头与代理规则，本次只完成源码和记录检查。
- 中心统一访问令牌的签发、内省、续期与撤销接口，以及统一用户授权目录；已有 OIDC 与后台授权接口不能直接假定满足共用令牌契约。
- 知识库生产与当前工作区存在发布记录已注明的差异，实施时选择明确基线，不把未发布业务改动带入桌面适配。
- 目标浏览器与基础屏幕尺寸；默认以当前 Chromium 桌面浏览器为首轮验证对象，再按使用范围扩展。
