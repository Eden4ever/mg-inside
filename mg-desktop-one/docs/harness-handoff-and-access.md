# 细化一：云端权限复用与跨人员流转

日期：2026-09-09。状态：对 [harness-plan.md](harness-plan.md) 第 4、5 节的落地细化，非新方案。

本文只回答两个问题：**"复用云端权限"具体复用什么、缺什么**；**一次交接具体传什么、谁能推动状态**。其余部分仍以主方案为准。

已按主方案确定的形态展开：**云端负责展示与协作事实，执行全部在本地 CLI，连接为主动出站、无需公网 IP**。这个形态带来两个必须正面处理的后果，本文第 2、6 节分别回答：撤销权限实际能做到什么（不能杀死本机进程），以及云端收到的证据哪些可信、哪些只是本机自述。

## 0. 本次核对得到的硬事实

以下结论来自本次读取源码，不是推测。它们直接改变实施顺序。

| 事实 | 依据 | 后果 |
| --- | --- | --- |
| `mg-desktop-one`、`mg-platform`、`mg-platform-kernel` 都不是 Git 仓库；`mg-auth-one-identity` 处于游离 HEAD | `git rev-parse` 逐仓核对 | **交接的"固定版本"目前没有载体**。这是唯一的 P0 阻塞 |
| 中心授权粒度只有"用户 × 应用"的布尔值（应用启用 ∧ 用户启用 ∧（直接授权 ∨ 角色授权）） | `src/application-access.js`、README"多角色与按主体授权" | 项目/环境/操作三个维度在中心不存在，必须在 Harness 自建 |
| AccessToken TTL 300 秒，`grant_types` 只有 `authorization_code` 与 `client_credentials`，**没有 refresh_token** | `src/oidc.mjs:33` ttl、`:30` grant_types | 长任务不能靠中心令牌续命；执行器不能缓存中心令牌 |
| 所有 OIDC 客户端都是机密客户端（`client_secret_post`，密钥 ≥32 位），同时强制 PKCE | `src/oidc.mjs:14,30-34` | 本地执行器**不能**做成独立 OIDC 客户端——那等于把客户端密钥装进每台开发机 |
| 回调地址精确登记，非 https 仅在 `NODE_ENV !== production` 且主机为 127.0.0.1/localhost 时放行 | `src/oidc.mjs:15-18` | 本地业务实例接**生产**中心时，`http://127.0.0.1` 回调会被拒绝，需要单独拍板 |
| 中心已提供 `/api/unified/introspect`、`/api/unified/revoke`，且内省时重新校验 session、`securityVersion` 与应用授权，不缓存 | README、`findAccount` 实现 | 撤销可以做到接近实时，不必自建吊销通道 |
| `token-one.api` 1.2.0 只登记了模型目录两个只读操作 | `mg-gateway/services/manifest.json` | 推理需直连网关或新增契约，试点期不要卡在这里 |

## 1. "复用云端权限"应拆成三层，只有前两层现在能复用

把一句话拆开，含糊就消失了：

| 层 | 内容 | 现状 | 试点做法 |
| --- | --- | --- | --- |
| L1 身份 | 你是谁：userId、姓名、部门、启停、`local_user_id` 映射 | **已具备**，OIDC + 内省直接可用 | 直接复用，本地不建用户表 |
| L2 应用准入 | 你能不能进这个系统（`harness` 这个 audience） | **已具备**，管理员在授权界面开关 | 新登记 `harness` 应用，用角色授权批量开通 |
| L3 业务权限 | 你在**哪个项目**、**哪个环境**、能做**哪个操作** | **不存在**，中心明确不管业务细分权限 | Harness 自建，但主体键用中心 userId，不建第二套账号 |

所以准确表述是：**复用身份与准入，自建项目内权限**。这不是妥协，是正确边界——中心一旦开始存"谁能发布项目 A"，它就变成了研发系统的一部分。

生效判定沿用主方案的交集式，但每一项都有明确归属：

```
可执行 = 中心应用准入(L2) ∧ Harness 项目成员角色(L3) ∧ 环境操作授权(L3) ∧ 本次任务委托范围
```

"本地测试环境能登录"永远只满足前两项。**测试环境的登录态不产生任何生产操作能力**——这条要写进接口守卫，而不是只写进文档。

## 2. 三类凭据的具体形态

原方案列了五类凭据，其中两类在当前中心能力下需要改形态。

| 凭据 | 签发方 | 有效期 | 携带什么 | 关键约束 |
| --- | --- | --- | --- | --- |
| 人员会话 | 中心 OIDC | AccessToken 300s / Session 12h | sub、identity_session、local_user_id | 工作台按标准流程取得；**不下发给执行器** |
| 设备凭据 | **Harness 云端**（非中心） | 长期，可吊销 | deviceId、绑定 userId、绑定项目集 | 一次性配对码建立；避开中心机密客户端的限制 |
| 任务委托凭据 | **Harness 云端** | 15 分钟，续约 | taskId、runId、userId、projectId、workspaceId、允许操作 | 续约时**必须**回中心内省一次，用户被停用/撤销授权/`securityVersion` 变化即断 |
| 推理凭据 | Token One | 按网关策略 | 模型授权与额度 | 不把桌面 Cookie 当模型 key |
| 发布执行器凭据 | 受控服务器 | — | 只对已登记目标环境 | 与编码进程隔离，试点期不发放 |

为什么执行器不做 OIDC 客户端：中心要求 `client_secret` ≥32 位且用 `client_secret_post` 认证，公共客户端流程（无密钥 PKCE）当前未开放，设备码流程也不存在。把密钥装进每台开发机 = 任何一台机器泄露即可冒充全体用户。**设备配对把这个问题绕开了**，代价只是 Harness 要自己管设备表——比在中心开一个公共客户端安全得多。

如果后续确实需要执行器直接持有中心身份，那是给中心提"公共客户端 + refresh_token"的正式需求，不是试点期的事。

### 撤销的六个检查点，以及撤销真正能做到什么

中心内省不缓存，所以只需在正确的时刻调用。以下动作**每次**都要重新校验，不看本地缓存：

认领任务 → 启动本地执行 → 提交结果 → 提交交接 → 接收交接 → 验收/发布。长任务每 15 分钟随委托凭据续约再校验一次。

**但要如实说明边界。** 执行全在本地 CLI、连接全是主动出站，云端没有反向控制通道，所以撤销权限的实际效果是：

| 撤销后 | 实际发生什么 | 生效时机 |
| --- | --- | --- |
| 本机正在跑的进程 | **不会被云端杀掉** | 不生效 |
| 下一次委托凭据续约 | 拒绝，CLI 停止领新指令 | ≤15 分钟 |
| 提交结果 / 提交交接 / 接收交接 / 验收 / 发布 | 服务端拒绝 | 立即 |
| 已下载到本机的源码 | **收不回** | 不生效 |

所以撤销是"止损"，不是"断电"。敏感项目真正控制的是**工作区下发范围**和**谁能成为项目成员**，不是撤销速度。云端应把该设备的在途任务标为"授权已撤销，结果不予采纳"，而不是显示"执行中"。

离线时：可以读已下载内容、写本地草稿；上述六个动作全部挂起，恢复连接后重校验。

## 3. 本地业务实例接哪个中心——必须拍板的一件事

本地业务实例要验证用户身份，就得指向某个 issuer。三个选项：

| 选项 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| A 指向本地/测试中心实例 | 复用现有 `mg-identity-service-test-db` 模式，本地 issuer | 测试账号与生产账号不是同一批，"同一个人"要人工对应 | 纯功能调试 |
| B 指向生产中心，回调用 https 回环域名 | 申请 `*.dev.meta-gravity.com` 泛解析到 127.0.0.1 + 证书，精确登记回调 | 需要一次 DNS 与证书投入 | **推荐**，试点期唯一能真正验证"同一个人"的做法 |
| C 由桌面/工作台代理回调 | 本地业务不直接接中心，走桌面 `/auth/start` 已有模式 | 本地业务要改接入代码 | 已挂载在桌面下的应用天然如此 |

选 B 的理由：试点要观察的是"跨人员交接"，如果每个人在本地是另一套测试账号，交接记录里的"谁交给谁"就是假的，指标全部作废。这一项投入不大但**不能省**。

生产中心不要为了调试放开 localhost 回调或通配回调——那会让任意本机程序截获授权码。

## 4. Harness 侧权限模型（自建部分的最小集）

只定义试点真正会检查的操作，不预先设计完整权限系统。

操作码（12 个）：`project.read` `requirement.write` `task.create` `task.claim` `run.execute` `handoff.submit` `handoff.accept` `test.result.write` `defect.create` `acceptance.decide` `release.prepare` `release.execute`

环境维度：`local` / `test` / `prod`。`run.execute` 与 `release.*` 必须带环境。

| 角色 | 授予的操作 | 明确不授予 |
| --- | --- | --- |
| 产品 | project.read、requirement.write、task.create、acceptance.decide | test.result.write、run.execute |
| 开发 | project.read、task.claim、run.execute@local、handoff.submit | **test.result.write**、acceptance.decide、release.execute |
| 测试 | project.read、handoff.accept、test.result.write、defect.create、run.execute@test | requirement.write、release.execute |
| 发布 | project.read、release.prepare、release.execute@prod | requirement.write、run.execute |
| 项目管理员 | 成员与规则配置 | 不自动获得上述业务操作 |

允许兼任：一个人可以同时是项目 A 的开发和项目 B 的测试。项目内兼任由项目配置决定是否允许（如"实现者不能自批发布"）。

**服务端校验，不靠前端隐藏按钮。** 首版验收标准第 3 条（开发用户直接调 API 提交"测试通过"必须被拒）就是在验这一条。

## 5. 状态机与转换守卫

```
需求草稿 → 待评审 → 待开发 → 开发中 → 待测试 → 测试中 → 待产品验收 → 待发布 → 发布中 → 已上线
```

每个转换的三要素——谁能推、必须附什么、失败去哪：

| 转换 | 需要的操作码 | 必须附带的证据 | 拒绝条件 |
| --- | --- | --- | --- |
| 需求草稿 → 待评审 | requirement.write | 正文 + 至少一条验收标准 | 无验收标准直接拒 |
| 待评审 → 待开发 | requirement.write | 需求版本号冻结 | — |
| 待开发 → 开发中 | task.claim | expectedRevision 匹配 | 已被他人认领 |
| 开发中 → 待测试 | handoff.submit | **完整交接包（见第 6 节）** | 工作区有未提交改动、自测未跑、缺依赖版本清单 |
| 待测试 → 测试中 | handoff.accept | 接收人确认接单 | 接收人无该项目 handoff.accept |
| 测试中 → 待产品验收 | test.result.write | 用例结果 + 被测 commit + 产物摘要 | 被测版本与交接包不一致 |
| 测试中 → 开发中（退回） | defect.create | 复现步骤 + 证据 + 对应版本 | 无复现步骤 |
| 待产品验收 → 待发布 | acceptance.decide | 验收结论关联到需求版本 | 需求版本已变更（须重测） |
| 待产品验收 → 开发中 | acceptance.decide | 不接受原因 | — |
| 待发布 → 发布中 | release.execute@prod | 已验收产物摘要 = 待发布产物摘要 | 摘要不一致、执行人无 prod 权限 |

独立状态：阻塞、取消、发布异常。**不允许用"改负责人"掩盖失败**——退回必须留缺陷记录。

失效规则：需求版本变更或代码基线变更后，旧的测试结论与验收结论保留历史，但**不能自动批准新产物**。实现方式是把 `requirementVersion + sourceRevision + artifactDigest` 三元组绑进验收记录，发布时比对。

### 5.1 失联不是失败

因为执行在本机、上报是主动出站，云端会经常看到"没有新事件"。必须把三种情况分开，不能都显示成"执行中"：

| 云端观察 | 判定 | 允许的操作 |
| --- | --- | --- |
| 心跳正常、有事件流 | 执行中 | 取消 |
| 心跳超时（如 >3 分钟） | **状态未知**，显示最后同步时间 | 只能取消；**不允许他人接管** |
| CLI 上报了终止结果 | 已结束（成功/失败） | 正常推进 |

"状态未知"不等于失败，也不能自动转成失败——电脑可能只是休眠了。另一台设备接管同一任务，必须先确认旧执行已终止（租约过期 + 执行代次递增），否则会出现两台机器同时改同一个任务的产物。

这条规则的存在理由很朴素：**下班关电脑是常态**，系统不能因此产生假的失败记录或双重执行。

## 6. 交接包：能自动采集的绝不让人填

这是"别让系统变成填表工作"的具体落实。**只有一个字段允许必填自由文本。**

新增一列"可信等级"——因为执行全在本地 CLI，云端看到的东西来源不同，可信程度差别很大：

- **权威**：云端自己产生的事实，本机改不了。
- **可复核**：本机上报，但云端能独立验证或重算。
- **自述**：本机上报，云端无法独立验证。本机用户能改自己的 CLI、测试脚本和退出码。

| 字段 | 来源 | 可信等级 | 人工介入 |
| --- | --- | --- | --- |
| handoffId、交接双方、时间 | 服务端生成 | 权威 | 无 |
| 需求版本 + 验收标准 | 引用需求对象 | 权威 | 无（产品填过一次） |
| repo + commit | CLI `git rev-parse HEAD` | **可复核**（云端向 Git 托管平台确认该 commit 存在且已推送） | 无；工作区不干净则拒绝提测 |
| 变更文件清单与规模 | `git diff --stat base..head` | 可复核（云端可自行重算） | 无 |
| 共享依赖版本 | 项目配置的兄弟仓库清单 → 逐仓 commit | 可复核 | 无 |
| 重建验证结果 | CLI clean-clone 重建（见下） | 可复核（受控环境可重放） | 无 |
| 构建产物摘要 | 构建输出 sha256 | 可复核（受控构建可复现） | 无 |
| 自测命令、退出码、日志 | CLI 记录本次运行 | **自述** | 无 |
| 运行环境说明 | 项目配置模板 | 可复核 | 仅当与模板有差异时补充 |
| 未解决问题与已知限制 | — | 自述 | **唯一必填自由文本** |
| 附件（截图、录屏） | 可选 | 自述 | 可选 |

**分级的用途只有一条规则：**

> 状态推进可以采信"自述"；**放权和发布只能采信"可复核 + 权威"**。

也就是说，开发上报"自测全绿"足以让任务进入待测试——这是协作效率需要的。但它**永远不能**成为跳过测试、或让产物直接进入发布的依据。发布前的关键检查由受控执行器对固定源码重新跑一遍，不看本机上报的退出码。

这不是不信任同事，是形态决定的：代码跑在别人的电脑上，你就没有办法用技术手段保证那台机器上的 `npm test` 是真的 `npm test`。把它标清楚，比假装它可信要好。

### 6.1 提测前的 clean-clone 重建验证

没有公网 IP，同事打不开你机器上跑着的服务。所以"接收方能不能在自己机器上把它跑起来"是交接成败的关键，而这件事**不能靠人写一段自由文本说明**。

做法：CLI 在生成交接包前，自动在临时目录做一次干净重建：

1. 从 Git 托管平台按 commit 重新 clone（**不是复制当前工作区**——那样会带上本机的未提交改动和本地缓存）
2. 按项目配置安装依赖（用锁文件）
3. 跑项目配置的启动检查与自测命令
4. 记录每一步的退出码与耗时

四步全过才允许提测。这一步的价值在于它验证的恰恰是本机工作区**掩盖**的问题：漏提交的文件、只存在于本机的环境变量、没写进锁文件的依赖、本地全局装了但别人没有的工具。

代价是提测慢几分钟。收益是"我这里能跑"这一类返工的主要来源被一次性消灭——而这正是试点要测的三个主指标之一（首次提测通过率）。

对于确实无法在开发机重建的项目（需要 Linux、独立数据库），退化做法是：跳过重建但**在交接包上明确标记"未经重建验证"**，让接收方知道风险在哪，而不是默默放过。

## 7. 试点范围：先不接 AI 引擎

**建议把引擎接入移出 1–2 周试点。** 理由：

要验证的假设是"跨人员交接能省多少事"。AI 编码是另一个独立变量，两个一起上，指标解释不清——省下的时间到底来自交接顺畅还是模型写得快，事后分不出来。而且引擎接入（Codex app-server 协议适配、Token One 工具循环验证、取消/恢复）本身就不止两周。

试点期开发人员**继续用手上现有的 AI 工具**，Harness 只负责需求、任务、交接、退回、验收。引擎接入放到试点结论出来之后，作为主方案阶段 1。

试点实际要写的东西（按依赖顺序）：

1. **给三个仓库做 Git 基线并推到共享托管平台**（P0，先于一切）。`mg-desktop-one`、`mg-platform`、`mg-platform-kernel` 建仓、定托管平台、拉成员权限；`mg-auth-one-identity` 从游离 HEAD 归位到分支。注意**本地 `git init` 不够**——第 6.1 节的 clean-clone 验证和接收方重建工作区都要求代码已推送到一个双方都能访问的远端。
2. 中心登记 `harness` 应用 + 回环域名证书（第 3 节选项 B）。
3. 云端四张表：Project / Requirement / Task / Handoff，加 AuditEvent。状态机接口按第 5 节表实现，服务端校验第 4 节操作码。
4. 工作台四个页面：任务看板、需求详情、交接包详情、接单确认。
5. 本地 CLI 最小版：配对、读 git 状态、按项目配置跑自测命令、做 clean-clone 重建验证、生成并上传交接包、断线缓存事件并补传。**不托管引擎、不跑发布**。

不做：引擎适配、发布执行器、多 Agent、插件、多项目、移动端。发布沿用现有脚本 + 人工确认，只在系统里登记"发布了哪个 commit"。

### 7.1 引擎路线：试点之后再定，但先定"怎么定"

试点期不接引擎，不代表不用想。这里只固定一条原则，避免被路线讨论提前绑架。

**不 fork 任何 Harness 内核。** 无论 Codex 还是 DeepSeek Harness，fork 的成本曲线是"第一天最低、第六个月最高"：上游每次更新都变成你的合并工作，而且你会连带继承它自己的 Session、用户、存储和权限模型——MG 已经有统一身份、应用授权和服务治理，再引入第二套身份/会话模型，需要长期做对账。这正是要避开的。

**正确的形态是：接口由你定义，引擎是可替换实现。**

```
MG Harness（需求/任务/交接/验收/发布——这是产品本体）
        │  自定义的窄接口：开会话 / 发指令 / 收事件 / 取消 / 恢复
        ▼
   EngineAdapter
    ├─ codex（首选试）
    └─ 其他（备选）
```

对引擎的需求其实很窄：在指定工作区跑一个带工具调用的循环，把事件流交出来，能取消、能恢复。围绕这四件事定接口，引擎换掉时改的是一个包，不是整个产品。

三条路线的实际判断（与外部建议不同的地方已标注）：

| 路线 | 表面成本 | 实际风险 | 结论 |
| --- | --- | --- | --- |
| Fork Codex 改成 Harness | 高 | 长期维护上游分叉 | 不做 |
| 自研 Harness + 引擎适配器 | 中 | 适配器要自己写 | **采用** |
| Fork DeepSeek Harness 当内核 | *外部建议评为"低"* | **实际不低**：内核处于开发者预览、接口会变；且要与 MG 现有身份/服务治理长期对账 | 不做；可作为引擎候选之一评估 |

需要留意的既有结论（见主方案第 6 节，均为 2026-09-09 查阅）：Codex app-server 官方对命令与 WebSocket 生产使用标注了实验/不支持边界；DeepSeek Harness 官方仍标为开发者预览。**两者都不适合让生产发布链路直接依赖其接口持续可用**——这也是把发布执行器与编码引擎隔离的另一个理由。

还有一个定位问题要挡住：不要在这一阶段把它扩成"企业智能工作台 + 多 Preset + 插件市场"。Preset 和插件生态是有了稳定闭环之后的扩展，提前做会让"验证交接能省多少事"这个目标彻底失焦，也会让 1–2 周的试点变成半年的平台工程。

## 8. 试点前必须有答案的四件事

1. **Git 托管平台定在哪**，三个仓库怎么划分。没有这个，交接包的核心字段是空的。
2. **本地业务接哪个 issuer**（第 3 节 A/B/C），决定"同一个人"是否成立。
3. **试点项目选哪个**——要选持续有改动、依赖少、产品/开发/测试三个角色齐全的内部应用。
4. **有没有共享测试实例**。这一项因为"本地 CLI 执行 + 无公网 IP"而更重要：同事**无法**打开开发者电脑上正在跑的服务。没有共享测试实例，测试人员只能在自己机器按 clean-clone 流程重建——可行，但每次提测多一轮环境成本，而且要求测试人员的机器具备完整开发环境。这会直接影响"交接等待"指标，要在试点前想清楚，不要中途才发现。

## 9. 观察什么

沿用主方案第 14 节指标表，但试点期**只认三个主指标**，其余作为背景记录：

- **交接等待**：交接包提交 → 下一角色实际接单的时长（这是最直接反映改善的量）
- **首次提测通过率**：首次正式提测后无需改代码即通过的任务占比
- **每任务人工补录时间**：人在系统里手工填写的总时长（这是新增成本，超过节省即为失败）

试点前和参与者约定可接受的幅度。10–20 个任务是方向性观察，不宣称统计显著。
