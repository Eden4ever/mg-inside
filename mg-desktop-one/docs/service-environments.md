# 服务环境发布与部署绑定

服务版本登记、业务程序部署、环境出口发布是三个步骤。版本及契约全局共享且不可覆盖；环境分别保存启用版本、部署绑定、修订号、审计与调用记录。正式桌面运行在 `production`，生产机目前只登记了真实生产环境，未用标签伪造测试环境。

## 发布流程

1. 将对应程序部署到可以独立核验的目标，检查实际产物、业务接口及契约。需要保留回滚能力时使用独立地址；不要覆盖仍被当前绑定使用的程序。
2. 通过服务管理登记不可变的服务版本和 OpenAPI 契约。
3. 发布工具登记部署的 `endpointRef`、环境、所属应用、实际提供应用、受控基础地址、部署标识、产物摘要、资源位置、部署时间，以及支持的服务版本和两份契约摘要。
4. 在服务目录选择环境，点击“发布部署”，核对实际提供方和运行资源，确认发布。后台在数据库锁内重读部署配置，再比较版本、契约、部署摘要和当前修订号。
5. 验证目标环境的真实出口。新配置不自动切换服务；只有显式发布才改变绑定。同版本也可切换部署；完全相同的重试不增加绑定修订或审计。

页面不能提交任意上游地址。旧页面缺少环境参数、修订号或部署摘要时拒绝写入。无匹配契约的历史版本不能发布；当前绑定与登记记录不一致时，该服务出口返回 503，不能自行猜测目标。

Office 的业务应用仍为 `office-one`，实际提供方为 Files 后端，受控前缀为 `/api/office`。权限校验继续按 Office 应用和个人文件执行。Token 仍绑定原服务器 `1.12.253.86` 的既有网关。

## 受控登记与新增环境

配置位于宿主机 `/opt/mg-desktop/config/services-deployments.json`，由 root 持有；整个目录只读挂载为 `/etc/mg-desktop`。桌面配置 `SERVICE_DEPLOYMENTS_FILE=/etc/mg-desktop/services-deployments.json`。运行账号不能从业务进程改写这个地址清单。

更新部署登记使用 `deploy/publish-service-deployments.py <新配置文件> <当前文件原始 SHA-256>`。工具先备份，使用文件锁和数据库 advisory lock 串行化操作，在锁内检查现有所有环境的有效绑定及新版本契约，以摘要防止覆盖另一发布，再原子替换配置。正在使用的记录不能被删除或修改；新增产物使用新 endpointRef，切换完成后才能删除不再使用的旧记录。失败后重新读取实际配置再判断，不盲目覆盖。

新增环境先用管理账号运行 `service-storage-admin.mjs environment`，显式设置 `SERVICE_ENVIRONMENT` 为新环境；仅创建空环境，不复制生产绑定。然后部署该环境的业务进程、登记其目标，配置该环境运行实例的 `SERVICE_ENVIRONMENT`。业务请求固定走所在实例的环境，用户传入查询参数不能把生产出口切到测试。管理页面可以查看已配置环境；非当前运行环境隐藏只读调用按钮，验收应访问该环境实际实例。

管理工具的数据库连接只从私密环境文件读取，不在命令或文档中写密码。`bind <部署文件>` 仅用于首次迁移已核验的当前六个服务；常规发布走页面/API 的明确选择，不能用初始映射脚本替代后续部署核验。`verify-bindings <部署文件>` 可读回核对。

## 数据升级与回退边界

本批在 `service_bindings` 增加五个可空字段：`endpoint_ref`、`deployment_id`、`deployment_digest`、`manifest_digest`、`contract_digest`。运行角色获得这些列的 UPDATE 权限，仍无建表权限。首次绑定保留六个启用版本，仅每个修订增加一次，并记录目标部署。13 个历史版本和既有审计、调用记录保留。

首次发布脚本在切换前备份数据库、服务环境配置与旧镜像；绑定或启动失败时恢复旧环境配置和旧程序，保留数据库里的新元数据，不以旧数据库备份覆盖后续写入。成功后若需要回退，须先核对当前实际绑定是否已改过地址，不能直接以旧程序的固定地址替代新的用户选择。后续程序发布继续保留只读配置挂载。

## 验证与后续范围

`npm run test:storage` 使用独立 PostgreSQL 和两个构建后的桌面 HTTP 进程验证生产/测试环境、部署切换、过期修订、摘要变化、未绑定拒绝、受控登记并发保护与恢复；路由目标使用可辨识的 HTTP 替身，不能据此宣称全部业务回归。

正式发布使用 `scripts/verify-service-bindings-deployment.py --capture` 取得一次不可覆盖的发布前基线，再用 `scripts/verify-service-bindings-deployment.py <发布号>` 核对正式镜像、六个绑定、历史数据及只读挂载；该基线校验针对本批首次绑定，不适用于未来有意更改绑定后的修订号。六服务的页面只读调用另行执行。

部署记录描述发布工具核验过的产物；当前没有持续侦测业务进程被外部替换，也没有把这些记录当作实时健康证明。生命周期后续已发布，见 [service-lifecycle.md](service-lifecycle.md)。自动部署流水线/注册 SDK、机器身份、细权限、健康过期与依赖关系仍按原规划推进。
