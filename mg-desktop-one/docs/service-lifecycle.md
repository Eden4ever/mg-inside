# 服务版本生命周期

生命周期属于服务版本，在所有环境之间共享。环境绑定仍分别决定该环境实际使用哪个版本。修改生命周期不会修改清单、OpenAPI 契约或部署产物，也不会删除历史版本。

| 状态 | 进入方式 | 调用与发布规则 |
| --- | --- | --- |
| 草稿 | 新登记的版本 | 必须选择已部署且契约匹配的目标完成首次环境发布；不提供调用。取消开发可在所有环境未使用时退役。 |
| 已发布 | 草稿首次成功发布，或从弃用恢复维护 | 可以按环境选择部署；停用某环境不改变全局生命周期。 |
| 已弃用 | 已发布版本填写迁移说明，可设置计划退役日期 | 已启用环境继续调用；不能新增或更换绑定，相同绑定重试允许。可以调整计划或恢复维护。 |
| 已退役 | 草稿或弃用版本通过跨环境使用校验后明确退役 | 任何环境均不能重新发布；保留版本、契约及审计，不能恢复，只能登记新版本。 |

旧数据没有生命周期字段时按“已发布”的历史登记语义兼容，版本与启用状态不变。这个兼容标签不证明旧版本仍有可部署产物，也不绕过既有部署契约校验。

## 页面操作

在服务目录点击版本详情，再点击“管理生命周期”。表单明确显示全环境范围，必须填写变更原因和迁移安排。计划退役日期按 UTC 日期解释；达到日期不会自动停服。日期未到时，显式退役也会被拒绝，需要先调整计划并通知调用方。

弃用显示说明和日期，目录分别展示生命周期与当前环境启用状态。退役前先把所有环境切换到替代版本，或明确停用；后台会列出仍在使用的环境。取消未提交表单会提示，失败保留输入，忙态阻止关闭。变更确认再次标明全环境影响。

生命周期变更使用独立修订号。旧页面不能覆盖新的计划；相同状态、说明、日期且修订匹配的重试幂等。版本清单重复登记不会恢复已退役状态。

## 后端与持久化

`POST /api/service-registry/lifecycle?environment=production` 由现有服务管理授权、平台管理员、提供应用访问权限和 CSRF 校验保护。请求字段为 `serviceId`、`version`、`status`、`reason`、`expectedRevision`，弃用时可附加 `retireAfter`。查询参数标识操作入口环境，不将生命周期限制为该环境。

`service_version_lifecycles` 独立保存每个服务版本的状态、原因、时间、操作者、修订与日期，外键关联不可变版本表。运行账号只拥有 SELECT、INSERT 及状态列 UPDATE，无删除权限。变更前后状态写入审计，在所有环境的管理视图中可见；不会把跨环境记录复制为新事件。

启用、生命周期修改及受控配置更新共用 PostgreSQL 全局事务锁。退役在同一锁内检查所有环境的当前绑定，因此另一个实例不能同时启用该版本。旧快照导入新环境时，也不能重新绑定已弃用、退役或草稿状态的全局版本。JSON 本地模式仅检查当前本地环境；外部持久化若不提供跨环境事务上下文，退役直接拒绝。

统一服务出口返回 `X-Service-Lifecycle`，弃用且有计划时还返回 `X-Service-Retire-After`，允许已授权的跨域应用读取这些头。它们是平台生命周期提示，不承诺实时上游健康。此功能管理统一出口，不会停止业务程序或撤销原有业务权限。

## 故障和回退边界

原有断库策略继续使用最后确认的路由快照，最长一秒的正常缓存及断库快照不保证立即感知另一实例的最新停用或生命周期变化。管理操作必须数据库在线，认证与数据权限仍实时走原链路。紧急权限撤销必须使用统一身份/提供方授权机制，不能把目录生命周期当作紧急安全封禁。

升级新增表，不改变历史契约和现有绑定。已经写入生命周期后，不能直接回退到不识别生命周期的旧程序，否则旧程序可能忽略退役限制；需要先审阅当前全局状态和绑定，选择支持生命周期的修复版本。生产发布保留数据库备份，不用旧备份覆盖新的用户操作。

## 验证证据

42 项桌面单测包含草稿首次发布、弃用与恢复、计划日期、退役后不可恢复、幂等、陈旧修订、重启和契约完整性。独立 PostgreSQL/真实桌面 HTTP 综合测试覆盖 CSRF 拒绝、跨环境可见、测试环境使用阻止退役、发布与退役竞争、旧快照导入拒绝、弃用响应头及原有断库恢复；实际路由目标使用 HTTP 替身，不能据此宣称业务全量回归。

正式页面验收选择未启用的 Office 1.0.0 历史版本，执行弃用后恢复维护，留下两条明确的验收审计；Office 1.1.0 及其他五个服务的绑定不变，六服务只读调用成功。未对生产启用版本执行停用或不可恢复的退役。
