# 服务管理应用研究

日期：2026-09-09。依据：用户提供的三张服务中心截图、通过 Codex 内置浏览器查看的 SuperBA 服务中心，以及前一轮检查的本地服务管理前端、共享契约、Java 平台内核源码和项目文档。本次为产品与实现方案研究，不包含业务代码修改、MG 生产核验或发布。参考系统只做页面查看与未提交表单的模式切换，退出时放弃输入，没有提交创建、编辑、关联、启停或删除操作。

## 1. 结论与定位

建议沿用参考系统的业务主线，将现有「服务管理」发展为「服务目录、API 管理、接入与发布、调用观测」一体化应用。面向平台管理员、服务提供者和有权限的调用者，解决四个问题：有哪些服务、怎样接入、哪个环境正在使用哪个版本、调用是否正常。实机研究确认需要分别建模服务与 API：服务承载接入配置，API 承载具体操作和文档，标签用于跨服务组织 API。

继续使用独立应用 `mg-service-one` 与 MG 公共应用壳。截图用于参考信息组织和业务流程，视觉、导航、窗口和表单继续遵循现有平台规范。

服务管理负责逻辑服务、接口契约、受控路由、环境绑定与观测。应用管理负责桌面入口与应用目录；资源管理负责机器、资源与部署信息；身份中心负责认证与授权。部署执行由既有交付工具承担，服务管理选择并发布已经核验的部署目标。

### 2.2 实查后的设计修正

1. 服务、API、标签分别有职责：服务管理路由接入，API 管理具体接口，标签跨服务关联 API。MG 还需保留已有版本和环境作为独立维度。
2. 服务详情下的接口列表应能进入独立 API 详情和编辑流程；只在版本抽屉里展示 OpenAPI 不足以覆盖参考系统的工作方式。
3. 「配置转发」和「登记接口」在参考系统中可以分开操作：所查看的自建服务处于启用状态，但关联 API 为零。这只证明 UI 允许该状态，不能证明未登记接口的转发行为。MG 可允许无接口的服务资产草稿；统一出口继续遵守已登记契约白名单。
4. API 启停若纳入 MG，应设计环境下的独立控制状态，并保留不可变契约；服务停用应覆盖该服务的全部 API 出口。UI 状态不能替代服务端和实际路由校验。
5. 服务关系图入口确实存在；本次查看的无关联 API 服务仅显示一个节点。没有取得多节点关系、边方向或自动调用链采集证据，不能把它认定为已验证的依赖拓扑。
6. 未见版本管理、环境切换、契约兼容检查等入口，不代表整个参考平台没有这些能力。MG 应保留本身已有治理能力。
7. 请求重试不能直接照搬默认 1 次：对写入和非幂等接口，建议默认不重试；只对符合幂等条件且结果可判定的失败启用有限重试，避免重复业务操作。

本次只验证了页面结构和查看行为。鉴权策略、TCP 实际转发、服务/API 启停效果、健康判定、统计完整性及计量公式均未做操作验证。新建 API 切换到 POST 后，当前所见表单仍以 Header/Query 为主，未观察到专用 Body 编辑区；MG 应基于 OpenAPI 明确支持请求正文，而不照搬这个可见缺口。

| 能力 | 本地证据 | 研究判断 |
| --- | --- | --- |
| 独立应用与导航 | `mg-service-one/application.json` 包含服务目录、调用记录、注册服务 | 沿用独立应用，调整信息架构 |
| 服务列表 | `src/App.vue` 按发布版本展示，提供应用筛选、搜索、前端分页 | 需要改为一个服务一行，版本移入详情 |

## 4. 推荐页面结构

一级导航建议为「服务管理、统计分析、标签管理」，与参考图的业务分组一致。注册服务改为服务列表的主要操作入口；调用记录和变更审计归入相应页面，不再与业务主线平级。

### 4.1 服务管理

- 左侧分类树：全部服务、系统服务、应用服务、数据服务、组件服务、引擎服务；名称来自截图，先作为可维护字典，需为每类补充定义，避免同一能力分类随意。
- 顶部筛选：环境、服务名称或标识、提供应用、启用状态、健康状态、标签。分类数量只统计有权查看的服务，并明确是否随其他筛选联动。
- 主列表：服务名称及标识、分类、提供应用、当前环境版本、接口数、启用状态、健康状态、最近检测时间、操作。
- 一个 `serviceId` 一行；历史版本、发布次数均不计入服务总数。没有环境绑定时显示「未发布」，不能把全部未启用版本计作停用服务。
- 主要操作：详情、发布或切换版本；停用、弃用和退役放入明确的变更流程。现有变更原因、修订号检查和审计继续保留。

服务详情采用「基本信息、接口、版本、环境部署、运行观测、变更记录」页签。接口页提供新建、查询、详情及编辑入口，API 详情包含调用地址、请求/响应结构和日志下钻。服务关系图在关系数据可验证后增加。列表负责扫描和定位，完整契约、版本比较和发布影响放在详情中。

### 4.2 新建与接入

建议分为四步：

1. 基本信息：服务名称、稳定标识、类型及子类、提供应用、负责人、描述、标签。已有服务登记新版时复用服务身份。
2. 接口定义：可视化维护操作标识、方法、路径、读写性质、Header/Query/Path/Body 参数、响应、错误码和示例；支持 API 标签及说明资料，同时保留 OpenAPI/登记包导入和校验错误定位。接口编辑生成新版本草稿，禁止原地改写已发布契约。允许先保存服务资产草稿，待接口完整后再发布。
3. 环境目标：选择已有受控部署目标，展示协议、主机、端口、前缀、实际提供方和产物标识。没有可选目标时允许仅登记草稿，后续再发布。
4. 核对与发布：显示契约差异、目标环境、地址和受影响版本；登记草稿与环境启用为两个明确动作。发布失败保留草稿和表单。

截图中的「英文名称」在本项目宜呈现为「服务标识」，允许现有 `files.api` 等合法标识，不能直接套用截图的字符限制破坏兼容。显示名称可调整，稳定标识不得通过普通编辑改变。

主机和端口属于部署目标，方法和路径属于接口。须分别展示统一访问地址、上游基础地址、操作路径及前缀改写规则，避免把不同含义放进一个「路由路径」字段。

第一阶段提供 HTTP/HTTPS 接入。原始 TCP 是独立转发能力，涉及监听端口、连接观测、网络授权及连接生命周期，不能通过增加协议选择按钮就声明支持，也不能套用 HTTP 方法或 OpenAPI 模型。

请求方法应按每个接口实际契约登记，默认不全选。健康探测只调用专用无副作用接口。文档中的 `servers`、任意 URL 或手填主机不能直接成为生产转发目标；新增目标仍由受控部署登记流程校验。

### 4.3 统计分析

沿用「服务列表、API 列表、图表分析」三个视图，并共享环境、时间范围、服务分类和标签筛选。现状库存与历史调用指标应有独立时间语义。

| 视图 | 建议内容 |
| --- | --- |
| 服务列表 | 当前启用状态与健康状态、调用次数、请求成功率、平均耗时、P95、接收与发送字节 |
| API 列表 | 服务、操作标识、方法、路径模板、调用次数、4xx/5xx、超时、平均耗时、P95 |
| 图表分析 | 请求量与错误趋势、延迟分布、流量趋势、异常服务排行 |

调用记录从服务或 API 行下钻进入，支持请求关联标识和失败类型；变更记录从服务详情进入。时间范围切换应保留筛选；空数据、加载失败与正常零请求采用不同状态。

### 4.4 标签管理

分类表达单一主归属，标签表达可叠加的业务域、用途等维度。环境、启停状态和真实健康状态属于结构化字段，不使用自由标签替代。

优先实现参考系统已经验证的「标签名称、关联 API 数量、跨服务 API 选择、查询与分页」。API 关联使用 `serviceId + operationId` 稳定标识，查询时再解析目标环境的有效版本；失效操作须明确显示，不能自动关联同名的新操作。

MG 可再扩展标签改名、颜色、停用以及独立的服务标签，但这些属于设计建议。被使用的标签优先停用；删除须先处理关联。分类和目录标签编辑单独审计，作为外部元数据保存，不回写已发布 OpenAPI；契约内部标签改变仍须登记新版本。

## 5. 状态与统计口径

必须区分三类状态：

| 状态维度 | 建议取值 | 解释 |
| --- | --- | --- |
| 环境启用状态 | 未发布、已启用、已停用 | 该环境是否允许经统一出口调用 |
| 版本生命周期 | 草稿、已发布、已弃用、已退役 | 全环境共享，沿用现有规则 |
| 健康状态 | 健康、异常、未知、不适用 | 独立于启用状态；无有效观测不能显示绿色 |

已启用的服务仍可能异常。停用只停止统一出口的调用，不代表业务进程已关闭。检测过期、采集故障或尚未检测显示未知；停用且不参与检测的服务显示不适用。

指标建议采用以下明确口径：

- 服务总量：权限范围内不同 `serviceId` 数量；环境已启用数和停用数单独统计，保留未发布数。
- 当前健康率：`健康的已启用服务 / 有有效健康结果的已启用服务`；同时展示检测覆盖率 `有有效健康结果的已启用服务 / 全部已启用服务`。分母为零显示无数据。
- 可用率：按时间窗计算的可用表现，需要持续采样或明确的请求型 SLI；不能以当前健康率替代。
- 调用次数：选定时间窗、环境与观测范围内的请求数。统一出口之外的直连流量，未接入采集时不计入。
- 请求成功率：建议以成功完成的 2xx/3xx 请求占纳入统计请求的比例展示，同时拆分 4xx、5xx、超时和取消；该指标不等同于业务成功率，业务成功需要提供方约定。
- 平均耗时：总有效耗时除以有效样本数；P95 使用可合并直方图或等价聚合，不平均各分钟的 P95。明确是否包含失败，流式请求另列首响应与完整连接时长。
- 请求速率：请求数除以所选秒数，单位 req/s；字节吞吐：实测传输字节除以秒数，单位 B/s；总流量为字节累计。未采集字节时显示无数据。
- 观测时间：记录统一时间基准，按用户时区展示；提供最后检测、最后采集和数据缺口。无调用不能推断健康，也不能生成零延迟。

需要专项验证网关异常计量：当前 `ApplicationGateway` 在结束回调中记录状态，状态未设置时使用 200，并有后续错误映射逻辑。统计建设前必须测试超时、上游断连和取消，避免失败或未完成请求被记作成功。

## 6. 实现边界与数据演进

建议扩展四类数据，并保留原有不可变版本和环境绑定：

| 对象 | 核心数据 | 规则 |
| --- | --- | --- |
| 服务资产 | serviceId、分类、负责人、展示信息、标签关联、修订号 | 可编辑元数据与不可变版本分离；旧契约内容不回写 |
| 分类与标签 | 稳定 ID、名称、分类层级、API 关联；可扩展颜色和停用状态 | API 标签通过 serviceId/operationId 关联；外部目录元数据与契约标签分离，变更留痕 |
| 健康观测 | 环境、serviceId、绑定修订、检测时间、结果、过期时间、原因 | 旧部署结果不能覆盖切换后的新绑定；过期降为未知 |
| 请求观测与聚合 | 环境、服务、版本、部署、操作、结果类型、耗时、字节、时间桶 | 原始记录和聚合分开存储，保留期限明确；敏感头和正文不默认采集 |

现有 `/api/service-registry` 同时返回版本、调用和审计，适合早期数据量。目录增大后拆为独立查询并在后端筛选、分页；统计按时间窗聚合，不能继续全量加载到前端计算。

前端扩展位于 `mg-service-one`；公共导航和组件沿用 `mg-platform`；管理接口与网关扩展以 `mg-platform-kernel` 为主，旧 Node 实现用于必要的兼容对照。

请求观测宜通过异步、有界采集交给独立聚合存储，避免每个请求结束都争用目录事务。第一阶段可先选用独立 PostgreSQL 表与聚合作业；若接入现有监控设施，再按实际查询量选指标后端，不提前引入整套复杂平台。采集丢弃、断库和队列溢出必须可见，不能影响业务出口可用性。

分类、标签、计数、详情与统计都继承服务及环境权限过滤；后续负责人权限不得只做前端按钮隐藏。跨服务统计和标签关联数量也不能泄露无权访问的服务。

## 7. 建议实施顺序与验收

| 阶段 | 交付范围 | 验收重点 |
| --- | --- | --- |
| 第一阶段：目录与接入 | 一个服务一行、分类、API 详情与编辑、API 标签关联、可视化登记、已有目标选择 | 多版本不重复计数；旧登记包可导入；表单和导入校验一致；并发修改、权限过滤和未提交保护有效；API 标签跨版本解析明确 |
| 第二阶段：真实观测 | 无副作用健康检查、过期机制、结果分类、持续采集与聚合、三类统计视图 | 超过 300 次仍统计正确；跨日及跨环境正确；超时/取消不记成功；字节实测；部署切换清除旧健康结论；数据缺口可见 |
| 第三阶段：治理扩展 | 负责人及环境细权限、依赖关系、告警、发布工具集成 | 变更影响可定位；权限由后端执行；告警基于真实观测且可关联恢复 |

TCP 转发、限流、熔断和机器身份按明确业务需求独立立项。参考系统的 TCP 表单已查看，但实际转发没有验证；不能把参考系统的页面能力当作 MG 的既有实现。
