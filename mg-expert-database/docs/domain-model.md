# 营商环境指标知识库领域契约

## 1. 目的与边界

本契约定义营商环境指标知识库 M0-M3 的统一业务语言、数据边界和状态规则。系统以**三级指标**为最小研究对象：一级、二级指标负责目录归类和汇总，不直接创建研究记录。

研究工作台固定展示八个研究模块。右侧的“AI指标专家”是基于当前三级指标、研究模块、依据材料生成建议的横向能力，不是现实专家名录，也不维护专家人员信息。

工作簿 `【0821】研究思路(1).xlsx` 是字段来源参考：其“指标画像、政策溯源、技术解码或数据链路、质量诊断、执行整改、优化迭代、总结概述、责任通讯录”被规范化为下述八模块。工作簿中的案例、政策和数值均为待核验业务资料，不作为系统预置事实。

## 2. 统一术语

| 术语 | 定义 | 不能混同为 |
| --- | --- | --- |
| 指标体系 | 某年度、某版本、某适用区域的一套指标目录和研究成果容器 | 单个指标或研究记录 |
| 指标体系版本 | 指标体系的可发布快照；发布后只读，修改必须复制为新版本 | 工作区草稿 |
| 指标节点 | 指标树中的一级、二级或三级节点 | 研究模块 |
| 三级指标 | 具有独立代码、考核口径和研究记录的叶子节点；也可称监测项 | 一级、二级汇总节点 |
| 研究记录 | 一个“指标体系版本 + 三级指标”对应的一份八模块研究底稿 | AI对话或附件 |
| 研究模块 | 固定编码的一个研究维度，独立查看、编辑、保存、确认 | 页面临时分组 |
| 研究结论摘要 | 由八模块内容汇总的摘要，不是第九模块 | 总结概述字段集合 |
| 依据材料 | 支撑研究字段的政策文件、数据来源、案例、附件或链接 | AI建议 |
| AI建议 | AI生成且等待人工处理的候选内容；可含依据引用与不确定项 | 正式研究内容 |
| 修订 | 对某一模块一次成功保存形成的不可变版本快照 | 浏览记录 |
| 模块确认 | 研究人员确认模块内容达到提交条件的动作；不等同于体系发布 | 审核发布 |

## 3. 聚合与关系

```text
指标体系版本
└─ 指标树（一级 → 二级 → 三级）
   └─ 三级指标（唯一可建立研究记录的节点）
      └─ 研究记录（1:1）
         ├─ 八个研究模块（固定 1:8）
         │  ├─ 依据材料（0:n）
         │  ├─ 修订（1:n）
         │  └─ AI建议（0:n，人工处理后才可写入）
         └─ 研究结论摘要（0:1）
```

关键基数和不变量：

- 一个指标体系版本中，同一父节点下的指标节点名称和编码不得重复；三级节点必须没有子节点。
- 研究记录的唯一键是 `(indicator_version_id, level_3_indicator_id)`；一级、二级节点不得创建研究记录。
- 每份研究记录必须拥有且仅拥有八个固定模块，模块编码不可增删改名；显示名称允许随模板版本调整。
- 模块内容、依据、修订和 AI 建议都必须关联到同一研究记录；引用不得跨指标体系版本。
- 发布后的指标体系版本、研究记录和已确认修订不得原地修改。必须“复制为新版本”后继续研究。

## 4. 八个固定研究模块

| 顺序 | 固定编码 | 名称 | 研究问题 | 工作簿来源 |
| ---: | --- | --- | --- |
| 1 | `portrait` | 指标画像 | 考什么 | 指标画像 |
| 2 | `policy` | 政策溯源与标杆案例 | 为什么考 | 政策溯源、典型案例 |
| 3 | `data` | 技术解码与数据链路 | 怎么考、数据从哪来 | 技术解码或数据链路 |
| 4 | `quality` | 质量诊断与问题归因 | 数据是否可信、问题为何发生 | 质量诊断 |
| 5 | `governance` | 管理体制与责任边界 | 条块权责如何划分 | 总结概述中的条块关系 |
| 6 | `rectify` | 分层整改与行动计划 | 怎么改、何时完成 | 执行整改 |
| 7 | `optimize` | 指标优化迭代 | 如何更科学 | 优化迭代 |
| 8 | `contacts` | 责任单位与联络机制 | 谁来干、如何协同 | 责任通讯录 |

模块定义、字段类型、填写阶段和必填规则以 [research-module-schema.json](research-module-schema.json) 为唯一机器可读来源。字段要求分为：

- `confirm`：确认当前模块前必须填写或明确标记“不适用并说明理由”。
- `publish`：提交指标体系版本发布前必须填写；发布规则可在未来按发布范围加严，不能放宽 `confirm`。
- `optional`：可保留为空，但应在有事实依据时补充。

## 5. 角色与权限

| 概念 | 权限 | 约束 |
| --- | --- | --- |
| `system_admin` | 管理用户、平台角色、全局模板和系统配置；默认拥有全部体系能力 | 不应以此绕过审计或发布规则 |
| 平台角色 | 用户账号分类，用于用户管理和界面展示 | 不限制具体指标体系中的实际能力 |
| 体系权限 | 由指标体系授权决定查看、研究、目录维护、审核和发布能力 | 同一用户可在不同体系拥有不同组合；除查看外的能力自动包含查看 |
| `ai_service` | 创建对话、建议和生成记录 | 不是人员角色；无正式内容写入、确认、审核、发布权限 |

非系统管理员的具体业务能力以 `IndicatorSystemAccess` 为唯一来源。`catalog_manager`、`researcher`、`reviewer`、`publisher`、`reader` 等账号值仅表示平台角色，不能裁剪体系授权。拥有体系研究能力的用户仍需被分派到具体三级指标后才能编辑该指标。

责任单位联系人属于业务联络信息，不属于“专家库”。M0-M3 仅记录单位、角色、公开工作联系方式和协同方式；个人手机、身份证件等敏感信息不得进入普通研究字段。

## 6. 查看、编辑和并发规则

- 打开工作台时所有模块默认处于**查看**状态。
- 每次编辑只针对一个模块。进入其他模块、切换三级指标、返回列表或关闭页面前，存在未保存修改时必须保存、放弃或继续编辑。
- 保存产生一条不可变 `ResearchRevision`，记录模块编码、保存前后版本号、操作者、时间和变更摘要。
- 客户端保存时必须携带 `revision_no`（或 `ETag`）。服务端版本不一致时返回冲突，不做“最后写入者覆盖”。
- 模块确认前，服务端根据 Schema 校验 `confirm` 字段、依据引用及不适用说明；失败时返回字段级错误。
- 模块确认后仍可被退回。退回不删除既有修订，而是创建新的可编辑工作版本。

## 7. 状态机

### 7.1 指标体系版本

```text
draft → researching → review → published → archived
                  ↘                 ↗
                    draft (复制新版本)
```

| 状态 | 含义 | 可执行转换 |
| --- | --- | --- |
| `draft` | 目录或研究底稿尚在准备 | `researching`、`archived` |
| `researching` | 可编辑八模块内容 | `review`、`archived` |
| `review` | 等待审核或存在审核退回 | `researching`、`published` |
| `published` | 对外或对内正式成果快照，只读 | `archived`；或复制为新的 `draft` |
| `archived` | 历史版本，不再作为当前工作版本 | 无原地恢复；复制为新的 `draft` |

### 7.2 研究模块

```text
not_started → in_progress → pending_review → confirmed
                  ↑              ↓              ↓
                  └── returned ──┘          returned
```

- `editing` 是短暂的前端会话状态，不持久化为业务状态。
- 模块只有在本模块必填字段满足且至少有一条有效依据材料时可从 `in_progress` 转为 `pending_review`。
- `confirmed` 仅表示模块审核通过；指标体系版本仍需整体发布。

### 7.3 AI 建议和依据材料

```text
AI建议：pending → accepted | rejected | superseded
依据材料：pending_verification → verified | invalid | superseded
```

- 采纳建议时必须选择目标字段或由研究人员编辑后保存；系统生成新的模块修订，保留建议原文、模型信息、依据快照和采纳人。
- 拒绝建议必须保留拒绝人、时间和可选原因；建议不可删除。
- `pending_verification` 依据可用于研究，但不能单独满足模块确认时的“有效依据”要求。

## 8. AI 横向能力契约

AI 的输入上下文至少包括：当前指标体系版本、三级指标完整路径、当前模块、已保存研究内容、已关联依据、用户问题和访问权限范围。AI 的输出必须包含：

1. 正文建议；
2. 目标类型（模块或研究摘要）、模块和建议字段；
3. 依据引用或“无可靠依据”的明确声明；
4. 置信状态（`supported`、`inference`、`needs_verification`）；
5. 需要人工核实的事项；
6. 生成时间、模型标识与提示词版本。

AI 不能将输出直接写入正式字段，不能确认模块，不能改变状态，不能发布版本。模块建议被人工采纳后产生模块修订；摘要建议被人工采纳后产生摘要修订。M0-M3 先落地建议、证据、修订和采纳接口契约；真实模型调用与流式对话属于 M4 实现范围。

## 9. 核心数据契约

| 实体 | 必要属性 | 关键规则 |
| --- | --- | --- |
| `IndicatorSystem` | `id`、`name`、`region` | 逻辑容器，可有多个版本 |
| `IndicatorVersion` | `id`、`system_id`、`year`、`version_code`、`status` | 发布后不可原地修改 |
| `IndicatorNode` | `id`、`version_id`、`parent_id`、`level`、`code`、`name`、`sort_order` | 仅 1/2/3 级；研究记录仅允许 level=3 |
| `ResearchRecord` | `id`、`version_id`、`indicator_node_id`、`summary`、`revision_no` | 一个三级指标一条记录，八模块固定 |
| `ResearchModule` | `record_id`、`module_key`、`status`、`content`、`revision_no` | `module_key` 必须是八个固定编码之一 |
| `Evidence` | `id`、`record_id`、`module_key`、`type`、`title`、`verification_status` | 可同时关联多个字段；不得跨版本引用 |
| `ResearchRevision` | `id`、`module_id`、`revision_no`、`snapshot`、`actor_id`、`created_at` | 追加式、不可变 |
| `AISuggestion` | `id`、`record_id`、`target_type`、`module_key`、`status`、`content`、`confidence`、`evidence_ids`、`source_revision_ids`、`model_id`、`prompt_version` | 可指向模块或研究摘要；采纳只产生对应修订，不直接覆盖正式内容 |
| `ReviewTask` | `id`、`version_id`、`scope`、`status`、`assignee_id` | 退回必须携带原因 |
| `AuditLog` | `id`、`actor_id`、`action`、`target_type`、`target_id`、`at` | 保存、确认、采纳、退回、发布必须审计 |

## 10. M0 需要确认但不得擅自虚构的业务参数

- 每个一级指标下实际二级、三级指标数量及指标编码规则。
- 发布范围（省级内部、地市协作或对外）和各角色的实际授权范围。
- 责任单位联络信息是否需要个人联系方式；若需要，必须补充数据分级、脱敏和访问控制规则。
- 政策、案例、数据源是否有正式采集接口、版权或访问授权。
- “全国前沿值”与“标杆案例”的权威来源、时间有效期和复核责任人。

这些参数在 M0 评审中确定后，才可进入 M2 导入模板和 M3 发布校验；不能以原型示例值替代正式业务规则。
