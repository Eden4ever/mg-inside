# 账户安全功能规划

## 证据基础

我检查了密码和企业微信登录入口，两条路径目前都直接签发完整会话。我们增加多因素后，必须共同经过最终验证关口，不能只在登录页增加按钮。详见[方案](proposals/auth-challenge.md)及[证据](context.md)。

## 约束

多因素默认关闭，由用户自行开启、关闭，不强制管理员使用。不引入付费认证服务；邮箱发送复用可用 SMTP，若没有免费可用的发信渠道则不启用邮件验证码。现有密码、企业微信与体系权限不变。

没有本地用户名或密码的账号首次登录后必须设置，完成前不能进入知识库；已有用户名保留。这个初始化要求独立于可选的 MFA 开关。

## 建议摘要

我们保留简洁的登录页：账户登录、通行密钥登录、企业微信登录；邮箱验证码作为可选账户登录方式。认证器六位码主要作为第二步，默认不提供“仅账户名加六位码”的单因素入口。开启多因素后，只能通过不同于首步的已绑定方式完成验证，邮箱不能连续充当两步。

用户可同时绑定邮箱、认证器和多把安全密钥，选择允许的第二步方式。邮箱可作为便捷补充验证，但不能声称与 TOTP/WebAuthn 等强度或符合 NIST 的 MFA。若选择邮箱作为备选，界面应说明其降低整个账户的恢复/验证强度。

## 下一步决策

建议按统一挑战方案实施；正式开发前确认是否接受邮箱作为较弱备选，以及现有 SMTP 是否可用。本轮仅规划，不实现新增认证接口，不采购服务。
