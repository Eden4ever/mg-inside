# 多模型协同研发：主代理、子代理与 Agent Harness

今天梳理了一套更适合小团队的 AI 协同开发方式：核心不是“哪个模型最强”，而是把不同模型当成不同角色，通过一个主代理统一调度，让其他模型作为子代理并行完成分析、设计、开发、测试和评审。

## 一、推荐的总体架构

- Claude Code：主代理 / 项目经理
  - 负责理解总体需求、拆任务、定义边界、制定接口契约、安排执行顺序、汇总结果和最终决策。
  - 更适合承担“全局统筹”角色，而不是亲自包办所有代码。
- Codex：核心工程执行代理
  - 负责核心代码实现、复杂修改、测试、Bug 修复、代码 Review。
  - 如果项目更偏纯代码开发，也可以让 Codex 作为主代理。
- Kimi：长上下文 / 资料理解代理
  - 适合阅读大仓库、历史文档、旧需求、长 PRD，并提炼成结构化上下文供其他 Agent 使用。
- DeepSeek：批量执行代理
  - 适合相对标准化、重复性较高的编码、测试用例、文档、代码整理等任务。
  - 可用于降低大量基础任务的模型成本。
- MiniMax：辅助分析 / 第二视角代理
  - 可承担长上下文分析、UI/前端建议、方案评审、第二轮检查等。
  - 更适合作为副脑或评审角色，而不是默认负责核心代码最终修改。
- ChatGPT：产品、方案与总结代理
  - 适合 PRD 梳理、产品方案、流程设计、跨角色讨论、复盘、培训材料和对外文档。

## 二、典型研发流程

1. 输入原始需求，由主代理整理目标、范围、约束和验收标准。
2. 主代理把需求拆成产品设计、技术设计、前端、后端、测试、Review 等任务。
3. 如项目上下文很大，先由 Kimi 等长上下文 Agent 阅读历史代码和资料，形成上下文摘要。
4. 主代理给不同子代理分配独立任务，能够并行的任务并行推进。
5. Codex 等执行 Agent 完成代码实现；DeepSeek 等处理测试、文档和批量任务；其他模型进行独立评审。
6. 各子代理只返回结构化结果，例如：完成内容、修改文件、关键决策、风险、测试结果、待解决问题。
7. 主代理综合各方结果，处理冲突和依赖，决定下一轮任务。
8. 最终只保留一个合并入口，由主代理或人工完成最终合并和上线确认。

## 三、关于子代理数量

通过命令行、API、脚本或自建调度器创建子代理，不会天然受 ChatGPT App 界面里类似“一个任务只能开几个子任务”的 UI 限制。理论上可以创建很多 Agent，但实际上会受到 API 并发、额度、成本、机器资源、文件冲突、任务依赖和主代理信息处理能力限制。因此重点不是追求 Agent 数量，而是建立合理的任务边界。实际使用中，建议先从 3～5 个稳定角色跑顺，再逐渐扩展。

## 四、上下文隔离是关键

主代理保留项目目标、核心需求、架构和接口约定、任务状态、关键决策、风险和最终结果。子代理只获得完成当前任务所需要的上下文，在自己的上下文窗口里完成大量阅读、分析和执行。子代理完成后，不应该把完整思考过程、日志和所有中间信息全部灌回主代理，而应该只返回压缩后的结构化结果。这样可以避免主代理上下文迅速膨胀，也可以让不同 Agent 独立思考，降低互相污染。

## 五、Agent Harness

Harness 可以理解为给模型套上的“运行框架”和“管理外壳”。它负责上下文管理、Agent 创建和销毁、任务拆分和调度、工具和权限控制、文件/工作区隔离、并发控制、Agent 间通信、结果压缩与回传、状态管理、测试、Review 和合并规则。最终想搭建的不是简单的“Claude 调 Codex”或“Codex 调 MiniMax”，而是一个多模型 Agent Harness：主代理像项目经理，各子代理像专业研发角色，Harness 则相当于整个研发组织的流程、制度、协作平台和运行环境。

核心原则：一个主控、多个专业 Agent、上下文隔离、结构化回传、接口契约优先、唯一最终合并入口。
