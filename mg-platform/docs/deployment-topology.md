# 应用分类与部署路径约定

状态：正式部署方案；当前本地联调仍使用独立端口。

| 分类 | 访问规则 | 部署入口 |
| --- | --- | --- |
| default 默认应用 | 所有登录用户可用；资源权限仍校验 | 桌面域名 `/apps/{appId}/` |
| system 系统应用 | 必须显式应用授权 | 桌面域名 `/apps/{appId}/` |
| internal 内部应用 | 必须显式应用授权 | 配置受信任的独立服务地址，可跨服务器 |
| external 外部应用 | 当前用户创建的个人外链 | 保留原网站地址，不接入可信认证桥 |

当前 personal-center 为默认应用；files 为规划中的默认应用。identity 与 app-manager 为系统应用。expert-database 与 Token 三个入口为内部应用。所有关联使用唯一 appId，不使用可修改的显示名称。

统一路径由反向代理/网关转发，允许系统应用与默认应用的服务仍独立构建、升级和部署，不强制单服务器或单进程。

## 推荐路由

桌面入口 `/`；系统应用 `/apps/identity/`、`/apps/app-manager/`；默认应用 `/apps/personal-center/`、`/apps/files/`。桌面的 `/auth/*` 与 `/api/*` 保留明确归属，不能与业务自己的 API 重名争用。

统一身份认证保留现有固定二级域名作为唯一认证服务地址（issuer、登录、授权、令牌及内省），桌面可以使用另一个二级域名。`/apps/identity/` 承载管理员界面，不建立第二套 issuer。登录流程由桌面跳到认证域名，再返回已登记的桌面 callback；不靠给所有子域共享可读 Cookie 实现登录。

例如现有 `identity.meta-gravity.com` 保持认证服务；桌面使用用户指定的新二级域名，其下部署默认/系统应用页面。更换桌面域名需要更新客户端回调、来源白名单及网关配置，认证 issuer 保持稳定。OpenID Connect 对 issuer 及发现元数据的一致性有明确要求，见[官方 Discovery 规范](https://openid.net/specs/openid-connect-discovery-1_0.html)。

接入应用需要声明 basePath，并统一处理构建资源基址、history 路由基址、业务 API 路径和登录回跳。浏览器刷新嵌套路由应返回该应用的 index.html，不回到桌面首页。SDK上报的是去掉部署前缀的应用内部路径，桌面根据注册项生成完整入口。

系统应用名称、图标、分类及路径元数据在平台公共目录维护；服务器地址、网关映射、凭据和环境配置在部署层维护。页面配置不得拼接业务服务密钥。

## 身份与隔离

保持统一认证提供同一套令牌，业务通过服务身份进行内省与逐请求授权。统一域名不代表免鉴权；各服务不能信任未经校验的客户端用户 ID 或角色。

同源系统应用属于同一信任边界，应全部为受控代码。外部网站不代理成桌面同源，避免把第三方页面提升为平台可信代码；内部异源应用通过严格来源与窗口身份校验的 SDK 通信。

## 落地顺序

1. 增加公共 basePath 约定和路径转换工具，验证根路径与子路径两种启动方式。
2. 先用个人中心验证 `/apps/personal-center/`，覆盖静态资源、刷新深链接、嵌入/独立访问、登录与退出。
3. 迁移应用管理及统一身份认证，单独核验登录/MFA/回调路径和各类 Cookie 的作用域。
4. 网关配置可回滚地切换正式入口，内部应用继续保持独立地址。新文件应用直接遵循该约定。

不在开发联调期间无准备地切换认证 issuer 或生产回调地址，避免造成已有统一会话失效。
