# 开发者中心与资源池规划

状态：设计阶段，尚未实现上传、模型审计或自动部署。

目标是由开发者上传标准应用包，平台完成审查和可验证的构建，在有权限的资源池部署，并把应用注册到现有桌面目录。开发者中心是交付入口；资源管理提供资源池、容量、网络和运行状态；统一认证提供人员、角色与部署权限；应用管理提供上架与可见性。

## 最小交付闭环

上传 → 检查清单及归属 → 隔离构建 → 规则扫描和测试 → 大模型审查 → 固定发布产物摘要 → 生成部署计划 → 选择已授权资源池 → 发布 → 健康检查 → 成功登记或回滚。

首版限定静态前端和标准 Node.js 容器服务。应用包包含版本化清单、源码／可追溯源码引用、锁文件、构建入口、健康检查、资源需求、所需配置与权限声明。纯二进制或镜像不能被宣称完成源码逻辑审计；缺少源码时标注审查范围与限制。

应用清单引用公共壳的名称、应用图标、导航及页面配置，不携带生产机密。应用 ID 由平台登记并绑定所有者，上传包不能自行冒用系统应用 ID。更新需要核验既有应用的发布权限，不能只相信包中的名称或 ID。

## 审查与发布边界

- 自动检查处理密钥泄露、依赖漏洞、包路径穿越／解压炸弹、容器权限、网络和存储声明、构建与运行测试。检查策略和结果均有版本号。
- 大模型负责解释结果、审查逻辑与设计、提出修复建议。包中的文档、代码注释和提示文本作为待审数据，不能成为审计代理的指令；审计环境没有生产凭据或部署工具。
- 构建器与审计器隔离运行，限制 CPU、内存、时间、磁盘和出站网络，不能挂载生产 Docker socket、主机目录或密钥。现有两台业务服务器不直接执行不可信上传包。
- 审计结论绑定包摘要、源码版本、构建环境、最终镜像摘要、扫描器版本和策略版本。更换代码或产物使旧结论失效，部署必须使用被审计的不可变产物。
- 有硬性失败项不能被模型的“通过”覆盖。低风险测试环境可按策略自动发布；生产发布由独立部署权限和具体部署计划控制，包含容量、端口、配置引用、数据库迁移、备份、健康检查与回滚影响。
- 灰度需要反向代理和多副本容量支持，不能把单实例替换称为灰度。数据库迁移通常不能通过换镜像自动逆转，需独立迁移和恢复策略。

## 资源池先行

资源池实体包含 ID、名称、环境、区域、服务器成员、可调度容量、CPU／内存配额、网络范围、允许的运行时、存储等级、部署角色、凭据引用和保留容量。服务器是资源，资源池是部署目标，不能把单个公网 IP 当作资源池标识。

现有两台服务器先登记为既有生产资源；不要自动纳入任意应用的通用资源池。平台核心服务和业务数据库设置保留容量与调度保护。建议另设隔离的构建／测试节点，是否新增机器及预算留待资源规划确定。

开发者可以从自己有部署权限且容量满足要求的资源池中选择。资源查看、凭据管理、应用发布、生产发布为独立权限。平台后端执行部署，开发者无须持有服务器密钥。

## 开源复用

- [Backstage 软件目录](https://backstage.io/docs/features/software-catalog/)：参考 YAML 元数据、应用所有权与统一开发者入口；已有本平台前端时可借鉴模型和集成方式，避免再建一套并行门户。
- [Harbor](https://goharbor.io/docs/)：可作为后续镜像与项目制产物仓库候选，首版也可接已有受控仓库。
- [Argo CD](https://argo-cd.readthedocs.io/en/stable/)：适合后续 Kubernetes 资源池的声明式交付。当前 Docker／systemd 服务器采用专用部署适配器，不能直接套用 Argo CD 代替主机运维。

先完成资源管理和标准应用清单，再建设最小上传／构建／审计／部署流水线；最后扩展多环境、灰度和多种运行时。
