# 平台统一授权规划

## 当前能力与后续目标

当前已支持应用级的直接用户授权、多角色授权及有效权限来源。应用内操作权限与数据范围尚未统一迁入，不应把应用入口授权误当成全部资源权限。

后续统一为一套平台角色模型：角色有多个，用户可加入多个角色；权限既可授予平台角色，也可直接授予单个用户。逐步迁移业务系统自己的重复角色模型，保留业务端权限执行。

## 授权对象与计算

授予对象为 userId 或 roleId。最终权限取直接用户授权与所属全部角色授权的并集，显示来源。撤销一份授权不否定其他仍存在的来源；界面在保存前说明撤销后是否仍有有效权限。第一阶段不引入显式拒绝规则，避免额外冲突优先级。

角色 ID、用户 ID、应用 ID 和权限 ID 都不可用显示名称替代。改名不迁移、不复制、不重置授权。

## 权限层级

1. 应用入口：是否允许进入某个应用。默认应用向登录用户开放入口，系统/内部应用需要授权。
2. 功能操作：如 `token-one-console:model.manage`、`expert-database:system.edit`、`files:file.share`，由应用注册定义。
3. 数据范围：本人、所属空间、指定指标体系或明确资源集合。操作权限不能自动扩大数据范围。

权限定义归属 appId，包含不可变 key、显示名称、说明、分组、风险级别、可配置数据范围类型、版本和停用状态。名称与分组可调整；删除或替换 key 需要迁移授权，不能静默遗留宽权限。

## 管理界面

保持“按用户／按角色”两个入口。选定授权对象后，按应用展示入口权限、功能权限及数据范围。提供搜索、有效权限预览和来源说明；不是从每个应用分别建立一套用户角色。

直接用户授权适合个别例外，岗位通用权限优先通过角色维护。新注册的管理权限默认不授予；平台管理员的恢复路径及最后一个可管理授权的账号需要保护。

## 执行边界

授权管理保存并计算权限，业务后端在每个受保护操作中校验应用 ID、权限 key 与资源范围。菜单和按钮只消费可见能力，不能作为唯一安全边界。内部应用部署到其他服务器不改变授权模型。

统一令牌仍由统一身份认证提供。权限变更不另造业务令牌；使用服务身份查询权限与内省。若引入缓存，必须明确定义授权版本与撤销时效；不可仅靠长寿命令牌中的旧角色列表执行撤权。

文件内容、指标体系等资源归属和数据查询过滤仍由相应业务服务执行；中心统一定义授权，业务确保所查资源确实属于被授权范围。

## 迁移步骤

1. 定义权限注册契约与应用清单校验，登记现有业务权限映射，不立即改变用户能力。
2. 以一个功能域试点，同时核对旧权限与新权限的计算差异，补齐跨用户/跨资源越权测试。
3. 经确认后切换该功能域后端授权来源，前端统一读取能力列表。
4. 逐步迁移剩余功能，保留有记录的回滚映射；最后删除重复业务角色逻辑。

不在一轮界面调整中直接移除全部业务权限检查。当前 Token One 控制台是用户明确要求的应用级管理能力入口，后续拆分具体权限时应显式映射其已授能力。
