## 目标与定位

新增独立应用“服务管理”，建议 appId 为 `service-manager`，项目为 `mg-service-one`，入口为 `/apps/service-manager/`。复用公共应用壳，在独立浏览器和桌面窗口中提供一致的服务目录。

各应用声明自己可供其他应用使用的 API，服务管理集中维护提供方、接口契约、版本、环境、使用方式、调用方及可用状态。业务请求继续由提供方处理，接入后的已登记接口通过统一出口；未改造应用保留现有代理。注册服务不会自动开通网络或授予业务权限。

| 平台应用 | 职责 |
| --- | --- |
| 应用管理 | 应用入口与个人外链 |
| 服务管理 | 应用对外提供的能力、接口契约、版本、调用关系 |
| 资源管理 | 服务运行在哪台服务器、部署版本与运行状态 |
| 统一身份 | 人员、角色、应用访问；逐步补齐操作权限和服务身份授权 |
| 开发者中心 | 后续构建、审查和发布应用时提交服务清单 |

## 首版页面

1. **服务目录**：按能力名称、提供应用、负责人、标签、环境及生命周期搜索。展示可用版本、认证要求和最近检查时间。
2. **服务详情**：概述、接口文档、版本记录、环境绑定、依赖与调用方。接口展示参数、返回值、错误和脱敏示例，可下载契约。
3. **注册与更新**：提交清单和 OpenAPI 文件，展示校验结果与差异，发布指定版本。支持负责人在界面上传，以及发布脚本提交。
4. **调用关系**：首版登记声明的依赖；后续接入实际授权、调用指标。明确区分“声明使用”“获准使用”“实际调用”。
5. **状态与变更**：登记记录、发布结果、契约变化、弃用日期和检测结果。健康检测不等于真实业务成功率。

## 服务模型

一个应用可以提供多个服务，一个服务包含多个 API 操作。同一后端可对应多个桌面入口，不按入口数量复制服务。例如 Token 门户、控制台和文档共享部署，但接口分组和权限仍独立；Office 当前接口由 Files 后端承载，必须同时记录能力归属与实际提供方。

| 实体 | 核心字段 |
| --- | --- |
| Service | 不变 serviceId、归属 appId、名称、说明、负责人、标签、可见范围 |
| ServiceVersion | serviceId、版本、契约摘要、不可变契约、状态、弃用说明 |
| Operation | operationId、方法、路径、认证要求、权限声明、副作用类别 |
| EnvironmentBinding | 环境、服务版本、受控 endpointRef、部署关联、当前发布摘要 |
| Registration | 来源应用、源码/发布摘要、提交身份、幂等键、校验与发布结果 |
| Dependency | 调用应用、目标服务、版本要求、是否关键依赖、声明来源 |
| Observation / AuditEvent | 检查时间、结果、来源；操作者、变更前后版本及请求标识 |

ServiceVersion 和 EnvironmentBinding 分开维护：升级测试环境不会改变生产指向。登记项、部署实例、接口操作各自使用稳定 ID，改名不改变关联。

## 注册契约与流程

应用仓库新增 `services/manifest.json` 和对应 `openapi.json`。HTTP 接口采用 OpenAPI 3.1 系列，首版实现时锁定经过解析器和校验器验证的具体版本；这是接口描述标准，运行部署与平台授权需要单独建模。[OpenAPI 官方规范](https://spec.openapis.org/oas/v3.1.1.html)

以下为建议清单，不代表已有接口和权限已实现：

```json
{
  "schemaVersion": 1,
  "appId": "resource-manager",
  "services": [{
    "serviceId": "resource-manager.inventory",
    "name": "资源台账查询",
    "version": "1.0.0",
    "contractFile": "./inventory.openapi.json",
    "ownerRef": "platform-operations",
    "visibility": "authorized",
    "operations": [{
      "operationId": "listResources",
      "effect": "read",
      "permission": "resource-manager:resources.read"
    }]
  }]
}
```

流程：应用生成清单 → 以绑定应用身份提交 → 校验归属、Schema、契约摘要和版本差异 → 保存待发布版本 → 发布成功并绑定目标环境 → 进入可发现目录。开发阶段可人工执行同一发布脚本，未来由开发者中心调用。

- 应用身份只能注册自己的命名空间；清单中的 appId 不能自证所有权。平台管理员可执行有审计的代登记。
- 同一服务同一版本同一摘要重复提交幂等成功；同版本不同内容拒绝，要求新版本。并发更新使用修订号。
- 首版离线上传完整契约，禁用远程 `$ref` 和任意 URL 抓取；限制文件大小、解析复杂度，渲染内容进行转义。
- 环境地址由受控部署绑定提供，不能直接信任 OpenAPI `servers` 并据此探测内网或发送凭据。
- 生命周期为草稿、已发布、已弃用、已退役。探测超时保留目录并标记状态过期，不能当成服务删除。
- 删除接口、增加必填参数、收紧响应或改变认证要求需要兼容性检查；发布说明列出受影响调用方。不能只依据版本号断言兼容。
- 回滚切换环境到已验证契约及部署版本；只回滚目录不会回滚实际业务程序。

建议注册 API 为 `POST /api/registrations`、`POST /api/registrations/:id/publish`；查询为 `GET /api/services`、`GET /api/services/:id/versions/:version`。具体命名在实现契约时冻结。

## 权限与调用方式

区分目录可见、注册维护、服务调用三层权限。拥有 `service-manager` 入口或能阅读文档，不代表能调用提供方的 API。

当前统一身份已支持应用级用户与角色授权；操作权限和通用机器调用授权尚未完整落地。首版可先完成目录与发布：读者有入口授权；维护者另需平台管理员资格或已验证的应用发布身份。不能为方便发布而把现有内省客户端 secret 当成任意业务调用通行证。

后续调用分为两种：用户操作使用现有统一会话，由提供方校验用户与数据范围；后台应用调用使用统一身份签发的独立服务身份，限定调用方、目标服务、操作及环境，并支持轮换和撤销。该能力须先在统一身份与后端 SDK 实现，再开放到服务管理界面。

浏览器不持有机器密钥，不根据注册目录任意转发统一用户令牌。公共调用 SDK 通过已配置的同源业务入口调用，服务发现不自动修改桌面代理白名单。首版文档只提供脱敏示例；在线调试后续先开放显式白名单的只读接口，写操作与费用型操作单独设计。

## 首批登记对象

| 提供应用 | 候选公共能力 | 首次接入处理 |
| --- | --- | --- |
| 资源管理 | 台账、部署关系、采集结果查询 | 首个只读样板；采集刷新单独标记副作用 |
| 文件 | 列表、元数据、上传、下载 | 保留文件所有者和配额检查；不公开存储路径 |
| Office One / Files | 文档创建、编辑会话、保存状态 | 明确实际后端归属；签名回调不作为通用调用服务 |
| 指标知识库 | 指标体系及知识内容查询 | 逐项核对现有路由和数据授权，未实现接口列为待建设 |
| Token One | 模型目录、推理、用量查询 | 区分用户会话与现有 API 凭据、计费与管理权限 |
| 统一身份 | 当前用户及受限授权校验 | 登录协议和内省保留专用接入，管理接口不默认公开 |

不会机械导入全部 controller 路由：先由应用负责人确定承诺给其他应用使用的接口，后台专用、引擎回调和运维接口单独标记或排除。

## 实施与验收

1. **P0：契约与公共接入。** 完成清单 Schema、归属校验、公共请求客户端；用资源查询和文件元数据形成两份真实契约。
2. **P1：可发布的目录。** 完成独立应用、数据库、文档浏览、版本比较、幂等注册、环境绑定与审计；部署到新服务器前评估容量。使用独立数据库/账号，不直接操作身份或资源业务表。
3. **P2：调用治理。** 统一身份补服务身份和细粒度授权，提供方落实校验，再补调用申请、依赖追踪、受控调试和真实指标。
4. **P3：发布集成。** 开发者中心发布产物携带服务契约，部署成功绑定版本，契约变化用于影响分析。网关、限流和统一流量治理按真实需求扩展。

首版验收必须覆盖：越权注册被拒绝、无权用户无法读取受限契约、同版本篡改被拒绝、重试不重复登记、测试/生产不串用、目录宕机不影响已有业务调用、健康信息过期可见、两应用真实契约与实际接口一致、独立浏览器与桌面均可用。不能仅用目录页面能打开作为完成依据。

公共能力拆分详见 [公共能力与应用壳演进](./shared-capabilities-plan.md)。
