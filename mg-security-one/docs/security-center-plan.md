# 安全中心应用规划

平台新增「安全中心」应用，集中查看登录历史与操作日志，并把目前散落在代码里的安全策略变成可配置项。参考项目为 SuperBA 安全中心（`222.143.33.224:8091/security/`），只作能力对照，不复制其实现。

## 参考项目的能力清单

三个一级页面：

- **登录历史**：全部/登录成功/登录异常筛选、账户下拉、日期区间、账户搜索；列为账户、登录时间、登录 IP、登录地、行为类型。
- **操作日志**：左侧按系统分组；筛选为操作类型、操作单号、操作账号、来源/模块/功能、日期区间、是否上链；三个视图（全部、本地、操作链）；导出当前页与导出全部；列为 ID、操作、来源、模块、功能、操作账号、IP 地址、操作时间、是否上链、上链状态，行操作为查看与存证。
- **安全设置**：安全访问（黑白名单、鉴权方式、登录时效）、数据安全（加密算法、数据水印含支持文件/水印日志/水印溯源、数据脱敏）、账户安全（密码策略、账户锁定）。密码策略提供高/中/低/自定义四档，自定义项为密码长度、复杂度、是否允许与用户名或姓名相同、使用周期。

## 我们的现状（已核对代码）

统一身份中心 `mg-auth-one-identity`：

- `AuthSession` 有 `ipAddress`、`userAgent`、`createdAt`、`lastSeenAt`、`revokedAt`、`expiresAt`、`authMethods`、`verifiedAt`。这是成功登录的原始素材，但会话过期或清理后历史即消失，不能当作登录历史使用。
- `User` 有 `failedLoginCount`、`lockedUntil`、`lastLoginAt`、`status`、`authSource`、`mfaEnabled`、`mfaMethods`。
- **账户锁定已经实现，但参数硬编码**：连续 5 次失败锁定 15 分钟，见 `src/auth.ts:75` 与 `src/zentao-auth.ts:47`。
- **登录失败不写审计**：失败路径只递增 `failedLoginCount` 后返回（`src/auth.ts:72-78`），没有任何可查询记录。这是「登录异常」当前最大的缺口。
- `AuditLog` 有 `action`、`result`、`actorUserId`、`actorName`、`actorRole`、`targetType`、`targetId`、`detail`、`at`，**没有 IP 列**。已记录的动作只有用户、角色、应用授权、微信目录同步、邮件配置等约七类。
- **密码规则只有长度 10–128**（`src/password.ts:8`），无复杂度、相似度、有效期，散列为 scrypt。

各业务应用各自有自己的 `AuditLog` 表（如 `mg-expert-database` 的版本级审计），字段形状相近但同样没有 IP，且没有跨应用汇聚机制。

平台应用注册（`mg-platform-kernel/docs/application-registration.md`）：

- 运行目录的唯一来源是 `SERVICE_DATABASE_URL` 指向的 `desktop_applications` 表，Java 内核只读该表，不再回退内置目录或展示 JSON。
- 登记通过显式清单导入：`java -jar app.jar desktop-applications migrate <manifest.json>`，字段为 `id`、`name`、`description`、`entryUrl`、`upstream`、`defaultPath`、`allowedPaths`、`allowedApiPaths`、`icon`、`kind`、`authorizationAppId`、`requiredRole`、`minWidth`、`minHeight`、`defaultMaximized`。同 ID 同配置幂等，不同配置拒绝整批导入。
- 展示用的名称、说明与图标资源键仍取自 `mg-platform/packages/frontend/config/application-catalog.json` 与 `assets/app-icons/`。
- 应用授权（audience）由统一身份中心负责，不复制到桌面数据库。

## 开源参考怎么用

不引入整套开源 IAM。我们已有统一身份中心在管登录、会话与 MFA，换 Keycloak/Zitadel 等于做一次身份体系迁移，代价远大于收益。开源项目按两种方式使用：

- **Keycloak 当规格书**：它的 password policy 与 brute force detection 配置项经过多年打磨（失败阈值、临时/永久锁定、退避时长、计数重置窗口、最大临时锁定次数），我们的「密码策略」「账户锁定」直接照它定字段，不自己臆造。它的 Login Events 与 Admin Events 两套事件表的划分方式，也正好对应「登录历史」与「操作日志」的分法。
- **中台Admin（Vue3 + TypeScript + Vite + Element Plus）与 RuoYi-Vue-Pro 当界面与字段参考**：前者与我们前端完全同栈，登录日志、操作日志列表可直接对照；后者的操作日志/访问日志/异常日志文档把字段设计写得很细。参考项目的界面风格本身就像这一系出来的。

数据水印、水印溯源与操作日志上链存证没有可直接使用的开源实现，是自研工程，不在近期规划内。

## 必须写在平台内核的部分

`mg-platform-kernel` 已经替代生产 Node 桌面后端，持有登录流程、应用目录和 Spring Cloud Gateway 应用代理。以下三项在内核之外补不了或补得很别扭。

### 一、客户端 IP 的采集与下传（第一期即需要）

`ApplicationGateway.outboundRequestHeaders()` 对上游请求头做严格白名单，只转发 bearer 令牌、`Accept-Encoding` 以及 `content-type`、`content-length`、`accept`、`x-csrf-token`、`range`、`if-none-match`、`if-match`、`last-event-id`。整个内核搜不到任何 `X-Forwarded-For`、`X-Real-IP` 或 `getRemoteAddress` 的处理。

结果是流量经过网关后，下游的身份中心和各业务应用看到的对端地址都是内核自己，不是真实用户。`AuthSession.ipAddress` 现在记的值在这条链路下不可信。参考项目的「登录 IP」和「IP 地址」是核心列，这个缺口只能在内核补：

- 网关必须先剥掉客户端自带的 `X-Forwarded-For` 等转发头，再由网关自己写入受信头，否则前端可以伪造 IP。
- 受信头加入出站白名单，传给上游应用与身份中心。
- 登录流程同样要把真实客户端 IP 交给身份中心，登录尝试记录才有意义。

### 二、操作日志的采集点应设在网关（决定第三期的可行性）

`/api/apps/**` 这条应用代理路由目前不做任何记录；只有 `/api/services/**` 在 `doFinally` 里调用了 `services.record(serviceId, operationId, actor, status, elapsedMs)`。

网关在处理每个请求时已经解析出：应用标识、请求路径、方法、操作账号（会话 profile 的 `sub`）、响应状态码、耗时，并且已经在响应头里写了 `X-Request-Id`。补上客户端 IP 之后，这些字段正好构成参考项目操作日志的骨架——来源、功能、操作账号、操作时间、结果。

采用这个方案，第三期从「逐个改造应用上报」变成「内核加一张表加一个过滤器」，各业务应用不需要改。代价与边界要认清：

- 网关只掌握 HTTP 层事实，不知道业务语义。参考项目里的「操作」描述和「模块/功能」分类属于业务语义，仍由各应用自己的 `AuditLog` 提供，两边通过 `X-Request-Id` 关联。
- 在内核建表意味着操作日志的主存储落在平台库，安全中心从平台库读，而不是从各业务库汇聚。
- 记录写入不能拖慢或影响代理请求本身，失败要吞掉，参照现有 `services.record` 的处理方式。

### 三、IP 黑白名单与登录时效的执行点（第五期）

网关和登录流程是平台唯一的流量入口，「安全访问」里的黑白名单和会话时效只能在这里执行。策略存在哪个库可以再定，执行点没有选择余地。

### 不需要改内核的部分

应用注册不需要动 Java 代码。`V2__desktop_applications.sql` 原本把 `icon` 限制为 `IN ('knowledge','token','identity','personal')` 的硬枚举，`V3__desktop_application_icon_keys.sql` 已经放开为 `^[a-z][a-z0-9-]{0,63}$` 正则；`kind` 取 `system` 或 `internal` 也都在允许范围内。安全中心直接走 `desktop-applications migrate` 清单导入即可，不必改代码或重新打包。

## 后端归属：内核是安全中心唯一的后端出口

`desktop_applications` 中一个应用只有一个 `upstream`。安全中心同时需要身份中心的登录数据和内核网关的操作日志数据，一个 upstream 指不到两处，因此内核必须作为安全中心的唯一后端出口，由它聚合各能力。

但登录尝试的产生点搬不进内核：密码校验、失败计数、锁定判定与 MFA 都在身份中心完成，内核网关只经手登录之后的请求。因此按「谁执行谁拥有数据，内核只做对应用的出口」划分：

| 能力 | 数据产生与存储 | 对安全中心的接口 |
| --- | --- | --- |
| 登录历史 | 身份中心 `LoginAttempt` | 内核转发 |
| 操作日志 | 内核网关新表 | 内核直出 |
| 密码策略、账户锁定 | 身份中心（由它执行） | 内核转发 |
| 登录时效、IP 黑白名单 | 内核（由它执行） | 内核直出 |

不把登录事件复制进平台库，否则会出现两个事实来源和一个同步问题；身份中心本来就拥有 `User` 与 `AuthSession`。

由此，身份中心的 `GET /api/login-attempts` 定位为内核调用的内部接口，不由应用直接访问；内核携带最终用户令牌调用，其平台管理员校验依然有效。

注册应用时 `upstream` 必须一次填对，指向内核。`desktop-applications migrate` 对同 ID 不同配置是拒绝整批导入而不是覆盖，后续改 `upstream` 需要走受控的数据库变更流程。即使第一期只有登录历史（直接指身份中心也能跑通），也应从一开始指向内核。

## 分期计划

### 第一期：应用骨架 + 登录历史

- [x] 身份中心新增 `LoginAttempt` 表与迁移 `20260909180000_login_attempt`：账户、账户显示名、结果、失败原因、来源、第二因素、IP、User-Agent、会话标识、发生时间；按时间、账号、账户和结果建索引。
- [x] 记录写入：成功在 `issueSession` 内与会话同事务提交并带上会话标识，覆盖本地、企业微信、禅道及 MFA 完成后的所有成功路径；失败在计数事务提交之后补写，覆盖密码错误、账号锁定、账号停用、禅道未绑定与并发争用，账号存在时关联到用户，账号不存在时保留输入账号。
- [x] 身份中心新增 `GET /api/login-attempts`：按结果、账号、用户和日期区间过滤，分页上限 100，按时间倒序，仅平台管理员可读。
- [x] 集成测试 `test/login-attempt.integration.test.mjs` 覆盖成功记录带会话与来源地址、未知账号记录、连续失败到锁定的原因区分、查询筛选分页与越权拒绝。

- [ ] 内核采集并下传真实客户端 IP，见上一节第一项。当前记录的是身份服务直接看到的对端地址，经网关后不可信。
- [ ] 内核新增安全中心后端出口，转发登录历史查询；应用 `upstream` 指向内核而非身份中心。
- [ ] 在统一身份中心登记 `security-center` 应用与 audience，配置授权。
- [ ] 在公共目录加应用条目与图标资源，按 `desktop_applications` 清单格式登记运行目录。

暂不做「登录地」——由 IP 反查归属地需要额外的离线 IP 库，先留空列或只显示内网/外网，第二期再定。

企业微信与统一认证回调的失败路径尚未逐一梳理，目前只保证成功侧完整；补齐放在第二期一并处理。

### 第二期：操作日志（身份域）

- 身份中心 `AuditLog` 增加 IP 与 User-Agent 列，并补齐现有动作的写入点。
- 定义统一的操作日志字段口径：来源（应用）、模块、功能、操作类型、操作账号、IP、时间、结果。现有 `action` 字符串需要映射到「模块/功能/操作」三级，映射表随各应用维护。
- 安全中心增加「操作日志」页，先只读身份域数据，支持筛选与导出当前页。

### 第三期：操作日志跨应用汇聚

这是工作量最大的一期，需要先定架构再动手。至少三种可选：各应用按契约推送到安全中心、安全中心定时拉取各应用审计接口、或统一写入共享审计库。选型要考虑各应用数据库独立、审计不可篡改、以及历史数据是否回填。

- 定义跨应用审计上报契约与鉴权方式。
- 改造 `mg-expert-database` 等已有应用作为第一个接入方。
- 安全中心的操作日志按应用分组展示，对应参考项目左侧的系统树。

### 第四期：安全设置 · 账户安全

- 密码策略落库：最小长度、复杂度要求（大写/小写/数字/特殊字符中至少含几项）、是否允许与用户名或姓名相同、使用周期。提供高/中/低三档预设与自定义。
- 账户锁定落库：失败阈值、锁定时长、计数重置窗口，替换 `src/auth.ts` 与 `src/zentao-auth.ts` 中的硬编码 5 次/15 分钟。
- 策略变更本身要写操作日志。
- 注意向后兼容：现有密码已按旧规则设置，收紧策略只能在下次改密时生效，不能把存量用户直接锁在门外；使用周期到期应提示改密而非拒绝登录。

### 第五期：安全设置 · 安全访问

- 登录时效：会话有效期、空闲超时、单账户并发会话上限。
- 黑白名单：按 IP 或网段限制登录来源，需要区分平台级与应用级。
- 鉴权方式：哪些登录方式启用（本地密码、企业微信、禅道、统一认证），是否强制 MFA。

### 不列入规划

- 数据安全整块（加密算法、数据水印、支持文件、水印日志、水印溯源、数据脱敏）。
- 操作日志上链存证与「操作链」视图。

这两块与参考项目的行业属性强相关，没有对口的开源可用，且都需要独立的基础设施。要做需要单独立项。

## 待决事项

- 第一期的登录历史只覆盖统一身份中心的登录。业务应用如果还有自己的本地登录入口，需要单独确认是否也要上报。
- 「登录地」是否要做，以及是否接受引入离线 IP 归属地库。
- 安全中心的可见性：是仅安全管理员可见的系统应用，还是普通用户也能看到自己的登录历史。两者的接口权限模型不同，影响第一期接口设计。
- 日志保留期限与归档策略。参考项目登录历史有三万余条，我们需要先定保留多久、超期是删除还是归档。
